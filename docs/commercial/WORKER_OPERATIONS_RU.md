# Фоновая очередь и heartbeat AsBoljam

API сохраняет задание и неизменяемый снимок входов. Отдельный `python -m apps.worker.main`
захватывает его атомарно. `started_at` идентифицирует именно этот захват и не меняется
при продлении аренды. Миграция0005 добавляет отдельный nullable `heartbeat_at`.

Во время вычисления и сохранения результата другой поток каждые30 секунд выполняет
короткую транзакцию. Она продлевает только задание со статусом running и тем же
started_at. Завершённые, отменённые и повторно захваченные задачи продлевать нельзя.
Время heartbeat не уменьшается при обратном скачке часов. Синхронизация серверных
часов всё равно необходима; резкий скачок вперёд может преждевременно истечь аренду.

После30 минут без heartbeat следующий worker возвращает задачу в очередь и заново
проверяет доступ и входные данные. У старого running-задания без heartbeat отсчёт идёт
от started_at. Старый обработчик может ещё выполнять CPU-работу, но его прежний
идентификатор захвата не позволяет сохранить результат после повторного захвата.
Продление и повторный захват сериализуются по одной строке jobs; публикация дополнительно
проверяет права организации/пользователя, отмену, источник и версию захвата.

## Обновление существующей установки

1. Остановить все старые workers и API. Одновременная работа старого worker с новым
   недопустима: прежняя версия определяет истечение только по started_at.
2. Сделать backup выбранной БД и проверить его. Для SQLite использовать
   `scripts/backup_db.py`; для PostgreSQL — штатный backup и восстановление в отдельную БД.
3. Указать ту же `DATABASE_URL` и выполнить `python database/migrate.py`.
4. Запустить API и worker одной версии. Не редактировать migration markers вручную.
5. Проверить сохранённые задания и результат нового тестового расчёта в своей организации.

Миграция не меняет прежние значения заданий и не выдумывает активность: heartbeat у
старых строк остаётся NULL. Данные и volumes при обновлении не удаляются. Не следует
возвращать прежние исполняемые файлы на новую схему; для отката восстановить проверенную
копию в отдельную БД и выбрать соответствующую версию приложения.

## Ошибки и остановка

SQLite BUSY/LOCKED при claim или publication повторяет свежую транзакцию с задержкой
0.25–2 секунды. При publication сохраняется уже рассчитанный результат, повторного
обучения из-за блокировки не происходит. Ошибка heartbeat даёт обезличенное сообщение
DATABASE_ERROR и повтор на следующем интервале; она не предоставляет право публикации.
Другие ошибки БД в основном процессе завершают worker безопасным сообщением.

Heartbeat означает доступ к БД из процесса, а не доказательство прогресса модели.
Вычисление запускается в отдельном Python-процессе. Родитель сохраняет heartbeat и
проверяет status, started_at, доступ пользователя и регистрацию источника примерно каждые
0.5 секунды; отзыв доступа или другой захват останавливает старое вычисление. Результат
по-прежнему публикуется только через атомарную проверку исходного started_at и доступа.
Первый SIGINT (Ctrl+C) или SIGTERM запрещает
новые захваты и даёт текущему заданию завершиться с heartbeat и сохранением результата.
Захват, завершившийся одновременно с сигналом, возвращается в очередь только при
совпадении идентификатора; отменённое или повторно захваченное задание не оживает.
Второй сигнал прерывает ожидание. SIGKILL, Windows Stop-Process/stop.ps1 и истечение
внешнего grace period остаются принудительной остановкой: задание может ждать аренду.
Compose даёт worker120 секунд перед принудительным завершением; это не обещание, что
любой расчёт уложится в срок. stop.sh сообщает об отправке сигнала, а не подтверждает выход.
Настоящий failover,
сетевые разрывы, нагрузка и управление несколькими production-узлами требуют отдельной
приёмки. Тесты моделируют истечение часов; реальное ожидание30 минут не проводилось.

### Ограничение времени вычисления

`WORKER_CALCULATION_TIMEOUT_SECONDS` задаёт целое число от1 до3600, по умолчанию900
секунд. Ошибка настройки останавливает запуск worker до открытия БД. Время считается
монотонными часами с запуска дочернего интерпретатора, включая импорт библиотек и
запись результата. При превышении срока процесс завершается, задача получает
`JOB_TIMEOUT`, результат не публикуется, worker может взять следующую задачу.
Это ограничение вычисления; ожидание блокировки БД при публикации остаётся отдельной
операцией. Зависшая проверка подключения к БД не мешает родителю остановить CPU по сроку.

Дочерний процесс получает только снимок расчёта и минимальное окружение OS/Python,
без DATABASE_URL, паролей и переменных API. Его stdout/stderr не попадают в логи.
Данные и результат передаются в приватной временной директории; результат публикуется
атомарным переименованием файла после полного JSON, поэтому большой ответ не блокирует
родителя заполненной pipe. Ответ ограничен128MiB. Файлы удаляются после успеха, ошибки,
таймаута или обрабатываемого прерывания. Временный диск должен иметь достаточное место
и защиту доступа; эта передача не является шифрованием данных на диске.

На Windows дочерний процесс скрыт; на POSIX он отделён от группы сигналов терминала,
чтобы первый Ctrl+C позволял текущей работе завершиться. Родитель при прерывании
делает terminate, затем при необходимости kill с ограниченным ожиданием. Pipe срока
жизни закрывается ОС при гибели родителя; отдельный поток ребёнка вызывает немедленный
выход. Этот поток зависит от планировщика Python: native-код, надолго удерживающий GIL,
может задержать реакцию на гибель родителя. Пока родитель работает, он принудительно
останавливает ребёнка по сроку независимо от GIL ребёнка. SIGKILL/TerminateProcess или
отключение питания не позволяют гарантировать удаление приватных временных файлов;
оператор проверяет оставшиеся `asboljam-calculation-*` в приватном системном temp.
Отзыв прав защищает публикацию немедленно на уровне БД; скорость освобождения CPU
зависит от доступности БД и планировщика ОС. Принудительное завершение всей машины,
исчерпание памяти и production failover требуют отдельной проверки.

## Проверка API перед запуском worker

`GET /api/v1/ready` возвращает200/ready только при доступной БД с ожидаемыми миграциями. Ответ503 содержит DATABASE_UNAVAILABLE либо MIGRATION_REQUIRED; проба не обновляет схему и не раскрывает детали подключения. `/health` остаётся проверкой живого процесса. Compose ждёт readiness API перед запуском worker/web. Зелёная проба не доказывает наличие самого worker или прогресс модели.

## Статус расчёта в web

После запуска видны очередь, выполнение или ошибка на KK/RU. При работающей задаче
показывается давность последнего heartbeat относительно времени ответа API. После90
секунд без ответа — предупреждение, а не утверждение о падении процесса. NULL остаётся
«нет данных». Heartbeat не измеряет готовность модели. При сетевой ошибке кнопка
«Проверить состояние задачи» повторяет только GET прежнего run_id; новый расчёт не
создаётся. При failed polling прекращается. История задач
доступна на страницах прогноза/закупки после reload: выберите прежний код, чтобы
продолжить проверку или открыть готовый результат. Список обновляется кнопкой,
разбит на страницы по20 и ограничен выбранным филиалом и типом расчёта.
Endpoints списка и статуса требуют текущую сессию, роль и org/branch scope;
операционный snapshot и payload не выдаются.
