# Backend persistence and migration

Local demo: `python database/migrate.py`, `python scripts/seed_demo.py`, `python -m uvicorn apps.api.main:app --port 8000`, and in another terminal `python -m apps.worker.main`.

`DATABASE_URL` defaults to `sqlite:///.../data/asboljam.sqlite`. To use PostgreSQL, install `requirements.lock` and set `DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/asboljam` before migration, seed, API, and worker. Never commit a real connection string. `database/postgres_schema.sql` is generated from the actual ORM models. Both SQLite and PostgreSQL were exercised: the isolated Docker project ran PostgreSQL 17.11 and passed its latest 19-test API suite, including worker calculations, isolation, concurrent approvals and native token rotation. [Runtime evidence](../artifacts/verification/postgres.json) records actual dialect, record counts, runtime versions and image IDs. These operational counts can include records created by runtime checks; the immutable supplied CSV counts remain in the data manifest/research provenance. Final suite counts belong to [FINAL_REPORT.md](../FINAL_REPORT.md) and [PROGRESS.md](../templates/PROGRESS.md).

The initial versioned migration (`0001`, recorded in `schema_migrations`) uses SQLAlchemy DDL, with one transaction. Repeated execution preserves data. There is no Alembic dependency in this implementation. Before future schema changes, add an explicit new migration and a backup/restore test; changing the model does not upgrade an existing database.

Current migrations are `0001`–`0005`: `0002` introduces organizations and a one-time legacy tenant backfill; `0003` adds import evidence, revisions and receipts without inventing legacy provenance; `0004` adds immutable `organization_sources` and permits `real_only`. Version `0004` rebuilds the SQLite organizations table transactionally or changes the PostgreSQL CHECK constraint in place. It preserves existing rows and never activates REAL or inserts source grants automatically. Unknown or incomplete migration histories are rejected. The tenant operator CLI requires the complete current migration set. Back up before upgrading and restore only to a new destination.

The nine operational source schemas are validated at import and persisted as typed JSON payloads with organization, kind, branch and canonical source key columns. Database uniqueness prevents duplicate source keys even under concurrent commits. References, units and ranges are checked transactionally by the importer; these JSON source references are not PostgreSQL foreign-key columns. This is a demo persistence design, not a complete stock-movement or accounting ledger.

Auth sessions contain only hashed opaque tokens. Passwords use salted scrypt. Web mutation requests need an allowed `Origin` and `X-CSRF-Token`; native requests use short-lived bearer access tokens plus one-use rotating refresh tokens. Reuse revokes the whole refresh family. `COOKIE_SECURE=true` is required behind HTTPS. Development defaults accept only `http://localhost:3000` and `http://127.0.0.1:3000`; configure `ALLOWED_ORIGINS` explicitly for deployment. No wildcard credentialed CORS is accepted.

The worker atomically claims queued rows, stores immutable input snapshots, and writes results, job state and audit together. A crashed worker's running job becomes eligible for retry after 30 minutes. The run ID is the result ID. Each run is side-effect free until persistence; workers never send supplier orders. Do not run tasks longer than the 30-minute lease without implementing worker heartbeats.

Backups: `python scripts/backup_db.py backup --database data/asboljam.sqlite --output backups/demo.sqlite`. Restore to a new path with `python scripts/backup_db.py restore --backup backups/demo.sqlite --destination data/restored.sqlite`. PostgreSQL uses `pg_dump` / `pg_restore` supplied with PostgreSQL, which must be verified in its deployment environment.

SQLite backup tests cover committed WAL content, integrity, restore fidelity, tampering and refusal to overwrite an existing destination. PostgreSQL restoration was independently exercised: [postgres-backup.json](../artifacts/verification/postgres-backup.json) records a 505217-byte dump, its SHA256, a fresh restored database, matching table counts, matching password hashes and restored migration state. This comparison does not claim a content hash comparison of every table or production recovery certification. The dump itself is private and remains under ignored `backups/`, outside Git and release archives. Preserve live databases and volumes while testing restoration in a separate destination; verify the target production recovery procedure separately.

[runtime.json](../artifacts/verification/runtime.json) additionally records 77 successful external HTTP checks through nginx with a separately running worker, including forecast/procurement completion and manager approval/export. That HTTP script does not itself establish the database dialect, cross-organization coverage or shortage-rejection behavior; its listed limits are complemented by the PostgreSQL integration suite rather than silently counted as extra coverage.

No seed runs at startup. The seed CLI accepts an optional `DEMO_PASSWORD` (minimum 12 characters) or prints one generated password exactly once. Re-running the seed preserves credentials. It allowlists nine CSV basenames; research-only oracle data and generator fields are excluded from storage and APIs.

The importer enforces each organization's policy: SYNTHETIC for `synthetic_only`, REAL for an operator-configured `real_only` organization, and no operational access for `unconfigured`. REAL is web-only and restricted to one immutable source/branch; `purpose=test_fixture` is visibly TEST, while `pilot` is PILOT. Source registration is permitted only on an empty active unconfigured organization, revokes prior sessions and records an opaque operator-declared authorization reference, not verified consent. The [REAL operator runbook](../docs/commercial/REAL_DATA_OPERATIONS_RU.md) describes preflight/apply, explicit closed-day origins, continuous history, exact inventory snapshots and source/date checks through import, worker and approval. Fixed demo dates are unchanged. Native REAL operations explicitly return 403.

The [offline POS adapter](../docs/POS_ADAPTER_RU.md) prepares explicitly mapped aggregate sales or inventory CSVs without connecting to this database. REAL rows retain REAL; successful offline preparation is not an API import or a source authorization. Dry run writes nothing, and opt-in output is confined to a new ignored `.cache/enterprise-adapter` directory. Its personal-data/oracle filters do not replace a complete privacy or authorization review. Real enterprise files, sensitive mappings and output bundles must not enter Git or a distributed source archive. A stock-movement ledger, worker heartbeat, native REAL support, target deployment and an actual business pilot remain separate unfinished work.

Migration `0005` adds nullable `jobs.heartbeat_at`; original job columns and started_at claim identity remain unchanged. A missing legacy heartbeat uses started_at for expiry. Stop old workers before upgrading: they do not understand heartbeat renewal. See [worker operations](../docs/commercial/WORKER_OPERATIONS_RU.md).
