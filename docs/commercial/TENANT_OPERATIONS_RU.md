# AsBoljam — создание и приостановка организации

Инструкция для оператора с разрешённым доступом к выбранной БД. `tenant` здесь —
отдельная организация со своими пользователями, филиалами и операционными записями.
Команды выполняются из корня проекта; они не отправляют приглашения, письма или заказы.
Само создание организации не является подключением реального бизнеса и не разрешает `REAL`-импорт.
Для отдельного перехода пустой `unconfigured`-организации к зарегистрированному REAL-источнику
используйте [REAL_DATA_OPERATIONS_RU.md](REAL_DATA_OPERATIONS_RU.md).

## 1. Выбрать БД и подготовить миграцию

Оператор задаёт `DATABASE_URL` явно в защищённой среде процесса. Проверить нужный сервер,
базу и окружение перед любыми изменениями. Не вставлять URL с паролем в команду, чат,
лог или Git; Python-команды ниже не читают `.env` автоматически.

Для локального упражнения можно выбрать отдельную SQLite-базу. При первом запуске
миграция создаст её по явно выбранному пути; команды управления организацией требуют
уже существующую мигрированную БД. `production` требует PostgreSQL, конкретные HTTPS
origins и secure cookies — условия описаны в [security runbook](SECURITY_RUNBOOK_RU.md).

Сначала проверить конфигурацию без подключения к БД:

```text
python -m apps.api.config
```

Перед обновлением существующей БД создать резервную копию и проверить её восстановление.
Для SQLite пример ниже использует обозначения путей; заменить их выбранными путями.
Назначение должно быть новым файлом:

```text
python scripts/backup_db.py backup --database PATH_TO_EXISTING.sqlite --output backups/pre_0004.sqlite
python scripts/backup_db.py restore --backup backups/pre_0004.sqlite --destination backups/restore_check_pre_0004.sqlite
```

Для PostgreSQL использовать `pg_dump` и `pg_restore` в новую отдельную БД с подходящей
версией утилит и безопасной передачей credentials. SQLite-команда не работает с PostgreSQL.
Наличие backup-файла не заменяет проверку восстановления.

Применить версии схемы к выбранной через `DATABASE_URL` базе:

```text
python database/migrate.py
```

`0001` создаёт исходные таблицы. `0002` добавляет `organizations` и один раз собирает
старые organization ID из пользователей, операционных записей, импортов, заданий,
прогнозов, планов, аудита и ключей идемпотентности. Старые строки, пароли и сессии
не перезаписываются. Для прежних организаций сохраняется `synthetic_only`; неизвестные
название/timezone остаются пустыми, provenance — `legacy_migration`. Для известного
`demo` заданы `AsBoljam Demo` и `Asia/Qyzylorda`.

`0003` добавляет доказательства импорта, ревизии и квитанции без вымышленного backfill.
`0004` расширяет политику до `real_only` и создаёт `organization_sources`, сохраняя
строки и прежние политики; сама миграция не регистрирует источники и не активирует REAL.
CLI требует все четыре миграции.

Повторный запуск не создаёт организации для новых строк без зарегистрированного tenant
и не заменяет отредактированные метаданные. Неизвестная или неполная история миграций
отклоняется. Не исправлять такую ошибку ручным удалением version marker. DDL, заполнение
таблицы и version marker одной миграции должны завершиться в общей транзакции.

Для этого workflow **не запускать `seed_demo.py` или demo launchers**, которые вызывают
seed. Они предназначены для отдельной демонстрационной базы. CLI управления tenant
сам не вызывает seed или миграции. Перед preflight и изменениями он требует точного
набора поддерживаемых версий; старая или неизвестная новая схема отклоняется без записи.

## 2. Выбрать политику данных

| Политика | Поведение |
|---|---|
| `unconfigured` — по умолчанию | Организация и первый admin создаются без данных; доступны вход, настройки и ограниченные операции настройки аккаунта. Операционный импорт и расчёты заблокированы. |
| `synthetic_only` | Допускается текущий учебный workflow с явно искусственными записями `SYNTHETIC`. Это не режим работы с настоящими продажами. |
| `real_only` | Не выбирается при bootstrap. Оператор однократно включает его через `configure-real` для пустой активной unconfigured-организации с известными метаданными и зарегистрированным источником/филиалом. |

Первые две политики не принимают REAL. Нельзя менять `data_origin=REAL` на `SYNTHETIC`
ради прохождения проверки. Для REAL нужны отдельная регистрация и явное назначение
`test_fixture` (результаты TEST) либо `pilot` (PILOT); сведения о разрешении заявляет
оператор, приложение не проверяет документ. Подробные preflight/`--apply`, отзыв сессий,
web-only ограничение и требования дат — в [REAL runbook](REAL_DATA_OPERATIONS_RU.md).
Заполненную организацию переключить нельзя. Для учебного сценария ниже политика
`synthetic_only` выбирается явно при создании организации.

## 3. Создать пустую учебную организацию

Сначала выполнить предварительную проверку. Пример использует только вымышленные
идентификаторы; название, timezone и email заменить осознанно:

```text
python scripts/manage_tenant.py bootstrap --organization-id training-fastfood --name "Training Fast Food" --timezone Asia/Qyzylorda --currency KZT --data-policy synthetic_only --admin-email owner@training.example --operator-id local-operator --reason "Create an empty synthetic training workspace"
```

Без `--apply` команда проверяет метаданные, отсутствие tenant, связанных orphan-записей
и занятого email; выводит `status: ready`, `branch_count: 0` и завершает работу без
создания организации. Предварительная проверка не резервирует идентификаторы: при
подтверждении условия проверяются снова. Email пользователя уникален во всей БД.

Для создания выполнить ту же команду с `--apply` в обычном интерактивном терминале:

```text
python scripts/manage_tenant.py bootstrap --organization-id training-fastfood --name "Training Fast Food" --timezone Asia/Qyzylorda --currency KZT --data-policy synthetic_only --admin-email owner@training.example --operator-id local-operator --reason "Create an empty synthetic training workspace" --apply
```

CLI дважды запросит пароль скрытым вводом. Требуется 12–1024 символа. Пароль не принимается
через аргумент команды или переменную окружения; перенаправленный stdin и ввод с
отображением символов отклоняются. Не помещать пароль в имя, reason или operator ID.
Отмена и несовпадение двух вводов не создают tenant. Передать владельцу пароль отдельно
по согласованному защищённому каналу; автоматической доставки нет.

При успехе появляются одна активная организация с `provenance=operator_bootstrap`,
один активный admin с пустым списком филиалов и событие `tenant.created`. Ни филиалы,
ни меню, ни остатки, ни прогнозы не создаются автоматически. `operator:local-operator`
в аудите — обозначение оператора БД, а не веб-пользователь с таким именем.

## 4. Добавить первый учебный филиал

Первый admin входит с созданным email/паролем. Для `synthetic_only` открыть импорт
филиалов, скачать шаблон `branches`, подготовить CSV и выполнить preview → исправление
ошибок → отдельное подтверждение. Пример одной искусственной строки:

```csv
branch_id,branch_name,data_origin
training-01,Учебный филиал,SYNTHETIC
```

После успешного commit филиал добавляется в разрешённые филиалы импортировавшего admin.
Далее загрузить справочники меню, ингредиентов, рецептур, поставщиков и предложений;
затем календарь, продажи и остатки с согласованными ссылками на эти ID. Все девять схем
и порядок подготовки описаны в [договоре данных](DATA_CONTRACT_RU.md). Другим сотрудникам
admin назначает роль и филиалы через управление пользователями.

Без истории продаж не появится содержательный прогноз; без рецептур/остатков/предложений
невозможно получить полный закупочный план. Не выдавать отсутствие данных за нулевую
потребность. Текущий сценарий остаётся учебным: история до 31.12.2025, день прогноза
и snapshot 01.01.2026. Timezone организации не переносит эти даты на текущий календарь.

## 5. Приостановить или возобновить доступ

Сначала проверить выбранную организацию и ожидаемый текущий статус:

```text
python scripts/manage_tenant.py status --organization-id training-fastfood --status suspended --expected-status active --operator-id local-operator --reason "Suspend the training workspace for maintenance"
```

Вывод `ready` означает только успешный preflight. Для изменения повторить с `--apply`:

```text
python scripts/manage_tenant.py status --organization-id training-fastfood --status suspended --expected-status active --operator-id local-operator --reason "Suspend the training workspace for maintenance" --apply
```

Приостановка блокирует вход/доступ организации, отзывает её web/native сессии и refresh
tokens. Задания `queued`/`running` получают `failed` с `JOB_ACCESS_REVOKED`; уже запущенное
вычисление может закончить расходовать CPU, но не должно опубликовать отменённый результат.
Завершённые планы, прогнозы и аудит сохраняются. Записываются события `tenant.suspended`
и `job.cancelled` для отменённых заданий. Чужие организации эта операция не затрагивает.

Возобновление также сначала проверить без `--apply`, затем применить:

```text
python scripts/manage_tenant.py status --organization-id training-fastfood --status active --expected-status suspended --operator-id local-operator --reason "Resume the training workspace after maintenance" --apply
```

Возобновление записывает `tenant.resumed`, но не восстанавливает отозванные токены и
отменённые задания. Пользователи входят заново; нужные расчёты создают повторно.
Индивидуально отключённые пользователи остаются отключёнными. `--expected-status`
защищает от применения команды по устаревшему статусу, но не является монотонной версией.

## 6. Ошибки и восстановление

| Код/результат | Действие оператора |
|---|---|
| `ORGANIZATION_EXISTS`, `EMAIL_EXISTS` | Проверить существующую цель; команда не перезаписывает её и не меняет пароль. |
| `ORGANIZATION_ORPHANED` | Разобраться с происхождением старых строк; не назначать нового владельца автоматически. |
| `STALE_STATUS`, `STATUS_UNCHANGED` | Прочитать состояние снова и определить необходимое действие; не менять expected status вслепую. |
| `PASSWORD_MISMATCH`, отмена скрытого ввода | Создание не выполнено; повторить после проверки цели. |
| `DATABASE_ERROR` | Проверить соединение, состояние схемы, фактическую организацию и аудит перед повтором. |

При потере соединения в момент commit нельзя по одной ошибке CLI заключить, дошёл ли
commit до сервера. Проверить состояние и аудит; повторный bootstrap не заменяет уже
созданного администратора. Для восстановления его доступа использовать процедуру
`manage_password.py` из [security runbook](SECURITY_RUNBOOK_RU.md).

При восстановлении backup всегда выбирать **новый SQLite-файл или отдельную PostgreSQL-БД**,
сохраняя исходное хранилище. Проверить версии миграций, строки, роли, вход и разрешённый
workflow до переключения сервиса. После восстановления старой копии могли вернуться
старые состояния сессий/доступов: повторить необходимые отзывы до открытия сервиса.
Не использовать удаление Docker volumes или общих таблиц как способ очистить одного tenant.

Пользовательского удаления организации и автоматической смены политики данных пока нет.
Эта инструкция описывает реализованные операции; выполненные тесты и границы проверок
фиксируются отдельно в `artifacts/verification` и журнале прогресса.
