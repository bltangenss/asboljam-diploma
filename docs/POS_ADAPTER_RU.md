# Офлайн-подготовка выгрузок POS

`scripts/adapt_pos_csv.py` готовит CSV двух типов — агрегированные дневные продажи и снимки складских партий — через явное сопоставление колонок. Скрипт использует только стандартную библиотеку Python, не подключается к POS, сети или БД. Совместимость с конкретным предприятием не проверена: реальная выгрузка и правила её формирования не предоставлены.

**Граница текущего продукта:** CSV с происхождением `REAL` остаётся `REAL`. Рабочий importer приложения сейчас принимает только `SYNTHETIC`; импорт реальных данных в приложение намеренно не реализован. Адаптер выдаёт для них `CANONICAL_REAL_IMPORT_UNSUPPORTED`. Не заменять метку на `SYNTHETIC`, чтобы обойти ограничение. Этот результат завершает только офлайн-подготовку, а не внедрение на предприятии.

## Проверяемые примеры

Все файлы в `examples/pos_adapter` — вручную созданные **SYNTHETIC** примеры, не выгрузки предприятия. Из корня проекта:

```sh
python scripts/adapt_pos_csv.py --source examples/pos_adapter/sales.synthetic.csv --mapping examples/pos_adapter/sales.mapping.json
python scripts/adapt_pos_csv.py --source examples/pos_adapter/inventory.synthetic.csv --mapping examples/pos_adapter/inventory.mapping.json
```

Без `--write` выполняется dry run: stdout содержит отчёт, файлы и БД не изменяются. Код выхода 0 означает успешную локальную проверку; 2 — отказ. Он не означает успешный импорт. Для явно запрошенного сохранения:

```sh
python scripts/adapt_pos_csv.py --source examples/pos_adapter/sales.synthetic.csv --mapping examples/pos_adapter/sales.mapping.json --write
```

Создаётся новый случайный каталог `.cache/enterprise-adapter/<id>/` с canonical CSV и `provenance.json`. Можно указать `--output-dir .cache/enterprise-adapter/my-first-run`; существующий каталог не перезаписывается. Выход вне этого игнорируемого дерева, симлинки и junctions запрещены. На Unix выставляются режимы 0700 для каталога и 0600 для файлов; на Windows это не заменяет проверку ACL владельцем. Не добавлять реальные исходники, результаты или mapping с чувствительными названиями в Git/ZIP.

## Контракт mapping

Сопоставление направлено от canonical поля к колонке источника: `"meal_id": "product_code"`. Каждый фактический операционный столбец обязателен; нельзя подставлять константы или выводить доступность, stockout, promo либо складской остаток из продаж. Неизвестные и несопоставленные колонки приводят к отказу; адаптер не удаляет их молча.

| Настройка | Допустимые значения |
|---|---|
| `mapping_version` | Строка `"1"` |
| `kind` | `daily_sales` или `inventory_lots` |
| `declared_data_origin` | Явное `REAL` либо `SYNTHETIC` |
| `declared_sales_unit` | Для продаж обязательно `portion` |
| `declared_currency` | Для продаж обязательно `KZT`; валюты не конвертируются |
| `delimiter` | Запятая, точка с запятой или табуляция; по умолчанию запятая |
| `decimal_separator` | Точка или запятая; по умолчанию точка; разделителей тысяч нет |
| `date_format` | `%Y-%m-%d`, `%d.%m.%Y`, `%d/%m/%Y`; по умолчанию ISO |
| `columns` | Все canonical поля сопоставляются источнику; `data_origin` можно брать из явной декларации |

Если источник содержит колонку происхождения, её обязательно сопоставить; каждая её запись должна совпасть с декларацией. Конфликт отвергается. Если её нет, отчёт помечает `origin_evidence=operator_declaration_only` — происхождение заявлено оператором, а не независимо подтверждено. Смена декларации не делает synthetic данные реальными.

Продажи требуют `date, branch_id, meal_id, units_sold, available_portions, stockout_flag, is_open, promo, price_kzt, data_origin`. Снимок партий требует `branch_id, ingredient_id, lot_id, snapshot_date, expiry_date, on_hand_qty, unit, data_origin`. Это фактические операционные схемы текущего importer с расширенным только в офлайн-адаптере происхождением REAL.

Даты — уже определённые предприятием бизнес-даты. Timestamp, timezone и границы смен автоматически не угадываются. ID сохраняются строками, включая ведущие нули; допускаются латинские буквы, цифры, `_`, `-`, длина 1–64. Продажи — неотрицательные целые порции, флаги 0/1, денежные и складские величины — точные Decimal-строки. Единицы склада только `kg` и `L`, без скрытого пересчёта g/ml/pcs. Число продаж не превышает доступное, закрытый день не содержит продаж. Дубли естественного ключа отвергаются всей пачкой. Истёкшие партии сохраняются: исключение их из использования относится к расчёту закупки.

## Ограничения данных и отчёта

- Разрешены UTF-8/BOM, максимум 20 MiB и 250000 строк. Пустые обязательные значения не становятся нулями. Любая ошибка означает ноль выходных строк; отчёт ограничен 100 ошибками и маркером остановки.
- Имена колонок, похожие на персональные данные, research/oracle и параметры генератора, отвергаются даже без mapping. Email, телефон с международным префиксом и длинные цифровые идентификаторы в значениях также отвергаются. Прямые пути `oracle`/`research_only`/`latent` запрещены.
- Это ограничивающий фильтр, **не полная система обнаружения ПДн**. Заголовки могут быть произвольными; предприятие обязано предварительно предоставить только разрешённый агрегированный операционный экспорт без клиентов, сотрудников, платёжных реквизитов и свободного текста. Консервативный фильтр может отвергнуть длинный числовой operational ID; исправление требует согласованного обезличенного справочника, а не отключения проверки.
- Stdout/ошибки не содержат исходных значений или полных путей. Provenance содержит SHA256 исходных байтов/mapping/output, origin evidence, количество строк, диапазон дат и явные статусы `import_performed=false`, `foreign_keys_checked=false`, `enterprise_compatibility_verified=false`.
- Справочники, права организации/филиала, соответствие единиц ингредиентам, версия рецептур, история изменений и существующие дубли БД здесь не проверяются. Примеры используют отдельные ID, поэтому их успешная подготовка не обещает успешный demo import.

## Следующий шаг для настоящего внедрения

Получить разрешённый образец агрегированного экспорта, формальное сопоставление и договорённость о бизнес-дате, пропусках, возвратах, единицах и происхождении. Затем спроектировать отдельно разрешённую REAL ingestion boundary, справочники, доступ и аудит; проверить транзакционный preview/commit и исключение real данных из публичных/research артефактов. До этой работы live REAL import остаётся заблокирован намеренной границей продукта и отсутствием фактических данных предприятия.

Проверки адаптера: `python -X utf8 -m unittest discover -s tests -p test_pos_adapter.py -v`. Fixtures тестов искусственные, в том числе проверки ветки `REAL`.
