# Операторская инструкция: источник REAL и даты расчёта

Этот документ описывает реализованный протокол одного источника и одного филиала. Он не подтверждает подключение реального предприятия, достоверность его выгрузок, результат пилота или готовность публичного развёртывания. Все примеры ниже относятся к **вымышленному, сгенерированному TEST-набору**.

## 1. Что означают режимы

| Политика организации | `data_origin` строк | Назначение результата | Поведение |
| --- | --- | --- | --- |
| `unconfigured` | Не задан | Не задано | Настройка учётных записей; операционные данные и расчёты недоступны |
| `synthetic_only` | `SYNTHETIC` | `DEMO` | Существующая демонстрация: история до 2025-12-31, цель 2026-01-01 |
| `real_only`, источник `test_fixture` | `REAL` | `TEST` | Проверка протокола REAL на явно сгенерированных данных |
| `real_only`, источник `pilot` | `REAL` | `PILOT` | Протокол отдельно согласованного источника пилота |

`REAL` в TEST-наборе означает формат и политику обработки источника, а не доказанное происхождение от предприятия. Метки `TEST`/`PILOT` нельзя опускать при передаче результатов. Выбор `pilot` оператором сам по себе не доказывает наличие разрешения или качество данных.

В одной организации нельзя смешивать `REAL` и `SYNTHETIC`. Заполненную демонстрационную организацию нельзя переключить в REAL. Для другого источника или назначения создают отдельную пустую организацию. Пользователь веб-приложения не может выдать себе разрешение REAL через импорт или настройки.

## 2. Резервная копия и миграция 0004

Работайте из корня репозитория с выбранной базой. Перед обновлением остановите процессы API/worker на время обслуживания и создайте резервную копию. CLI управления организацией требует явно заданного `DATABASE_URL`, существующей базы и полного набора миграций `0001`–`0004`; сам он не мигрирует и не запускает demo seed.

Пример PowerShell для существующей локальной SQLite-базы; пути выбраны для стандартного расположения проекта. Имя резервной копии должно быть новым:

```powershell
$env:DATABASE_URL = 'sqlite:///data/asboljam.sqlite'
python scripts/backup_db.py backup --database data/asboljam.sqlite --output backups/before-real-0004.sqlite
python database/migrate.py
```

Переходите к миграции только после успешного backup. Утилита сохраняет согласованный SQLite snapshot, включая зафиксированные WAL-транзакции, проверяет integrity/FK и создаёт manifest с SHA256. Для PostgreSQL нужен штатный `pg_dump` и отдельная проверка восстановления через `pg_restore` в **новую** базу; SQLite-утилита PostgreSQL не обслуживает. Строки подключения с секретами не помещают в команды, документы или логи.

Миграция `0004` расширяет ограничение `organizations.data_policy` и создаёт `organization_sources`. Она **не активирует REAL**, не создаёт источники задним числом и не изменяет существующие данные, учётные записи или историю импорта. SQLite обновляет таблицу организаций внутри транзакции; PostgreSQL меняет CHECK-ограничение в транзакции. Неизвестные будущие версии или неполная история миграций отклоняются. Не исправляйте маркеры вручную. SQLite с нестандартными индексами, триггерами или внешними ключами к `organizations` требует отдельного разбора, а не принудительного обхода проверки.

При восстановлении используйте новый путь, проверьте восстановленную базу и только затем отдельно выберите её для запуска:

```powershell
python scripts/backup_db.py restore --backup backups/before-real-0004.sqlite --destination data/restored-before-real-0004.sqlite
```

Восстановление старой копии не является миграцией вниз работающей базы. Не перезаписывайте исходную базу. Производственный режим конфигурации требует PostgreSQL, HTTPS origins и secure cookie; эти настройки сами по себе не активируют REAL и не подтверждают безопасность развёртывания.

## 3. Создание отдельной TEST-организации

Следующие команды используют вымышленный адрес `owner@fixture.invalid` и источник `generated-fixture`. Они не создают реальный бизнес или внешнюю учётную запись. `DATABASE_URL` должен уже указывать на нужную мигрированную базу. Не используйте `scripts/seed_demo.py` для этого сценария.

Сначала preflight создания пустой организации:

```powershell
python scripts/manage_tenant.py bootstrap --organization-id real-protocol-test --name "Generated Protocol Test" --timezone Asia/Qyzylorda --currency KZT --data-policy unconfigured --admin-email owner@fixture.invalid --operator-id fixture-operator --reason "Create generated protocol fixture"
```

Если выбранная организация и база верны, выполните ту же команду с `--apply`:

```powershell
python scripts/manage_tenant.py bootstrap --organization-id real-protocol-test --name "Generated Protocol Test" --timezone Asia/Qyzylorda --currency KZT --data-policy unconfigured --admin-email owner@fixture.invalid --operator-id fixture-operator --reason "Create generated protocol fixture" --apply
```

Пароль первого администратора вводится дважды скрыто в интерактивном терминале. Не передавайте пароль аргументом, через pipe или текстом в файле инструкции. Создаются организация и администратор, **без филиала, продаж и остатков**.

## 4. Однократная регистрация источника

Preflight проверяет активную организацию с политикой `unconfigured`, известным названием, корректным IANA timezone и валютой KZT. Организация должна быть пустой: запрещены даже каталоги/филиалы, неуспешные preview, задания, результаты, импортные квитанции, ревизии, idempotency и операционный аудит. Учётные записи, сессии и разрешённая история администрирования этому не мешают.

```powershell
python scripts/manage_tenant.py configure-real --organization-id real-protocol-test --source-id generated-fixture --mapping-version canonical-v1 --branch-id 001 --authorization-reference fixture-ref-001 --purpose test_fixture --operator-id fixture-operator --reason "Enable generated protocol fixture"
```

Для применения повторите команду с `--apply`:

```powershell
python scripts/manage_tenant.py configure-real --organization-id real-protocol-test --source-id generated-fixture --mapping-version canonical-v1 --branch-id 001 --authorization-reference fixture-ref-001 --purpose test_fixture --operator-id fixture-operator --reason "Enable generated protocol fixture" --apply
```

Без `--apply` обе команды выполняют только preflight. Проверки повторяются внутри транзакции применения. Регистрация источника версии `1`, переход в `real_only`, отзыв доступа старых сессий/refresh-токенов и запись аудита атомарны. После применения **заново войдите через веб-интерфейс**. Старые сессии не становятся действительными после повторного входа. Организация с заданиями уже не проходит проверку пустоты; смена политики не служит способом переноса старых расчётов.

Параметры `source_id` и `mapping_version` — ASCII-идентификаторы до 64 символов из букв, цифр, `_ . : -`. `authorization_reference` — такой же непрозрачный идентификатор до 128 символов. Он ссылается на документ, который хранится у оператора: не вставляйте сюда содержание согласия, имя человека, email, путь к файлу, токен или пароль. Приложение **не проверяет** содержание документа, подлинность источника или правовое основание обработки.

Для отдельно согласованного настоящего пилота допустимо `--purpose pilot` вместо `test_fixture`; это новая отдельная организация с собственным источником, а не переименование вымышленного TEST. В этой инструкции такой пилот не создаётся.

В текущей версии одна организация имеет один неизменяемый источник и один зарегистрированный `branch_id`. Отдельного оператора редактирования источника или перевода TEST → PILOT нет. Не меняйте строку источника напрямую в базе. `mapping_version` фиксирует заявленную версию преобразования выгрузки; приложение не выполняет автоматически интеграцию с кассой или внешней системой.

Режим REAL обслуживается веб-приложением. Для native Bearer-сессии операционные маршруты REAL отвечают `403 NATIVE_REAL_UNSUPPORTED`; отдельные маршруты учётной записи/настройки остаются доступны. Это явное ограничение, а не подтверждение готовности мобильного REAL-сценария.

## 5. Подготовка и импорт девяти CSV

После повторного входа сначала импортируйте `branches` с **точно зарегистрированным** идентификатором `001`. Затем справочники `meals`, `ingredients`, `suppliers`; после них `recipes`, `supplier_offers`, `calendar`, `daily_sales`, `inventory_lots` с существующими ссылками. Импорт филиала выдаёт импортирующему администратору доступ к нему; доступ остальных пользователей настраивается отдельно.

Шаблоны CSV скачиваются на странице импорта. REAL сохраняет те же девять схем; обязательные заголовки приведены ниже. Порядок столбцов может отличаться, набор — нет.

| Вид | Обязательные столбцы |
| --- | --- |
| `branches` | `branch_id,branch_name,data_origin` |
| `meals` | `meal_id,meal_name,base_price_kzt,data_origin` |
| `ingredients` | `ingredient_id,ingredient_name,unit,reference_cost_kzt,shelf_life_days,yield_factor,storage_capacity,data_origin` |
| `recipes` | `meal_id,ingredient_id,net_qty_per_portion,recipe_version,data_origin` |
| `suppliers` | `supplier_id,supplier_name,lead_time_days,data_origin` |
| `supplier_offers` | `supplier_id,ingredient_id,pack_qty,unit_cost_kzt,min_packs,max_packs,lead_time_days,data_origin` |
| `calendar` | `date,branch_id,weekday,temperature_forecast_c,synthetic_event,is_open,data_origin` |
| `daily_sales` | `date,branch_id,meal_id,units_sold,available_portions,stockout_flag,is_open,promo,price_kzt,data_origin` |
| `inventory_lots` | `branch_id,ingredient_id,lot_id,snapshot_date,expiry_date,on_hand_qty,unit,data_origin` |

Для REAL во всех строках нужен `data_origin=REAL`; в полях филиала — зарегистрированный `branch_id`. TEST-набор должен быть явно сгенерированным для этого протокола и сохранять метку TEST в результатах. Не переименовывайте реальные неизвестные данные в SYNTHETIC и не выдавайте преобразованный demo-набор за предприятие.

Идентификаторы остаются строками (`001` не превращается в `1`), даты — `YYYY-MM-DD`, десятичные количества и цены — с точкой, флаги — `0`/`1`. Сохраняйте единицы: kg и L не складываются. В REAL лишние столбцы, включая генераторские `demand_multiplier` и `base_daily_demand`, отклоняются. Исследовательские/oracle-файлы не являются операционными CSV.

`available_portions`, `stockout_flag`, `is_open`, цена и promo — обязательные сведения, а не поля для произвольных нулей. Если предприятие их не учитывает, сначала нужен согласованный способ получить или достоверно восстановить их; текущий контракт не подменяет неизвестное нулём. В календаре поле `synthetic_event` сохраняется ради совместимости схемы, но для REAL должно быть **0**. Модель не использует его как признак.

На странице импорта `source_id` и `mapping_version` автоматически берутся из регистрации и недоступны для изменения. API повторно проверяет совпадение. Схема действий: файл → preview → разбор ошибок/изменений/полноты проверки → commit. Ошибочный или неполностью проверенный пакет не изменяет операционные строки. Счётчик разобранных строк не равен числу полностью проверенных ссылок; смотрите `validation_rows_checked`, `validation_complete` и `scan_complete`.

Полученный CSV-текст и нормализованные строки имеют отдельные SHA256. Указанный загрузчиком `declared_original_sha256` остаётся **заявленным, непроверенным**: `original_hash_verified=false`. Совпадение хеша полученного текста не доказывает подлинность исходной выгрузки.

Повторные коммиты, просмотр истории и исправления действуют по [инструкции импорта](IMPORT_OPERATIONS_RU.md). Для REAL дополнительно проверяется зарегистрированный источник. Коррекции поддержаны только для `daily_sales`, `calendar`, `inventory_lots`, по существующему ключу и с причиной; это новые ревизии, а не удаление истории. Изменившиеся входы требуют пересчёта неутверждённого плана; ранее утверждённая история сохраняется.

## 6. Выбор дня прогноза и остатков

Для REAL поле `origin` задаётся явно: это последний день наблюдённых продаж, который войдёт в расчёт. Он должен быть **раньше текущего бизнес-дня** организации. Бизнес-день вычисляется из текущего UTC-момента сервера и зарегистрированного timezone, например `Asia/Qyzylorda`; он не берётся из даты компьютера пользователя. Система не подставляет в REAL демонстрационные даты.

Каждое блюдо, присутствующее в используемой истории филиала, требует минимум **84 последовательных дневных наблюдения** от своей первой записи до `origin` включительно, без пропусков. Позднее появившееся блюдо с короткой историей тоже блокирует расчёт. Пропущенный день не считается нулевыми продажами. Нулевую строку можно записать только при известном факте нулевых продаж с корректными остальными полями. Продажи позже `origin` не участвуют в этом прогнозе.

Горизонт — один день: `target_date = origin + 1 день`. Импорт продаж текущего/будущего бизнес-дня отклоняется; дата снимка склада не может быть позже текущего бизнес-дня. Поэтому обычный сценарий — закрыть вчерашние продажи, предоставить снимок на начало сегодняшнего дня и рассчитать сегодняшний план. Исторический расчёт разрешён с явными прошлыми датами и пометкой `historical`.

Для закупки нужен снимок `inventory_lots` **строго на `target_date`**, до операций этого дня. Последний имеющийся снимок другой даты не заменяет нужный. Для каждого ингредиента рецептов прогнозируемых блюд требуется запись: известный нулевой остаток отражается строкой с `on_hand_qty=0`; отсутствие записи даёт `INVENTORY_COVERAGE_REQUIRED`, а не ноль. Единицы должны совпадать со справочником ингредиентов.

В контракте источника версии `1` партия с `expiry_date >= target_date` пригодна, в том числе в день истечения; более ранняя исключается. Текущий однодневный закупочный расчёт допускает к покупке только предложения с `lead_time_days=0`. Это фиксированные правила версии, а не индивидуально согласованная политика любого предприятия. Не подменяйте реальное время поставки нулём ради прохождения расчёта.

Результат сохраняет источник, назначение TEST/PILOT, timezone, UTC-время запуска, `origin`, целевой день и день снимка. Задание worker и утверждение проверяют этот контекст. Однако загруженный сегодня исторический снимок **не доказывает**, что именно эти данные были известны на прошлую дату: полноценного учёта «когда факт стал известен» и исторических версий всех справочников пока нет.

Цель прогноза — наблюдённые `units_sold`, не скрытый неудовлетворённый спрос. Текущие признаки используют строгую прошлую историю продаж и календарные даты. Наличие погоды, promo, availability или stockout в CSV не означает, что все они входят в модель. Закупочный расчёт дополнительно использует рецепты, выход, остатки, упаковки, цены, ограничения бюджета и вместимости. Человек проверяет дефицит и утверждает план; утверждение не отправляет заказ поставщику.

SYNTHETIC-демонстрация сохраняет `origin=2025-12-31` и `target_date=2026-01-01`, независимо от сегодняшней даты. Её историю не переносят на текущий календарь ради вида актуальности.

## 7. Отчёты, блокировка и текущие границы

CSV-экспорт операционных REAL-данных содержит дополнительные `usage_mode`, `source_id`, `mapping_version`, `source_version`; имя файла помечается `TEST-` или `PILOT-`. Экспорт плана содержит его контекст и строки расчёта. Это **отчёты, не канонические шаблоны повторного импорта**: лишние столбцы будут отклонены строгим импортёром. Для повторной загрузки используйте соответствующий шаблон и сохраните исходный отчёт отдельно.

При необходимости оператор приостанавливает организацию через `manage_tenant.py status` с ожидаемым текущим статусом и причиной, сначала preflight, затем `--apply`; подробности в [инструкции управления организациями](TENANT_OPERATIONS_RU.md). Приостановка отзывает сессии и отменяет ожидающие/выполняющиеся задания. Возобновление не восстанавливает старые сессии или отменённые задания и не меняет источник.

Остаются отдельной работой: проверка на согласованных данных предприятия, POS/складские интеграции и учёт движений склада, многодневный горизонт и поставки с положительным сроком, переходы между источниками/филиалами, настоящая производственная инфраструктура и её восстановление, мобильный REAL-сценарий. Пока нет измеренной экономии предприятия, гарантии качества входных данных или доказательства полезности прогноза для конкретного бизнеса. Эта инструкция описывает работающие границы протокола; выполненные проверки и их окружение фиксируются отдельно в отчётах проекта.
