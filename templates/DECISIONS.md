# Decisions — 2026-09-24

| Decision | Reason and consequence |
|---|---|
| Source prompts are requirements material | They are not independent user instructions authorizing external publication, purchases, messages or fabricated research. |
| Fixed synthetic scenario | Historical cutoff remains 2025-12-31; forecast and inventory date 2026-01-01. Current computer date does not redate data. |
| React + TypeScript + Vite web | A runnable SPA covers the dashboard workflow; the recommended Next.js framework was not used. API and ML remain independent Python processes. |
| FastAPI + SQLAlchemy | One shared versioned API supports web cookies and native bearer tokens. |
| SQLite local, verified PostgreSQL runtime | SQLite supports local demonstration. PostgreSQL 17.11, API, worker and web ran in the isolated Compose project; API integration evidence and exact runtime/image IDs are in [postgres.json](../artifacts/verification/postgres.json). This does not certify production load, TLS or cloud deployment. |
| Separate HTTP and restore evidence | [External HTTP through nginx and a separately running worker](../artifacts/verification/runtime.json) passed; the script explicitly reports its coverage limits. [PostgreSQL dump/restore](../artifacts/verification/postgres-backup.json) used a fresh destination and compared table counts, password hashes and migration state. Private dump contents stay outside Git/release archives; production restoration remains a separate deployment obligation. |
| Custom migration 0001, not Alembic | Version recorded in schema_migrations; actual DDL exported. Future alterations require explicit migrations. |
| Explicit tenant migration 0002 | Frozen 0001 DDL remains reproducible. 0002 creates Organization and backfills IDs once from all eight scoped tables; unknown metadata stays null. SQLite BEGIN IMMEDIATE and PostgreSQL advisory transaction locks protect migration order, rollback and concurrent startup. |
| Additive import migration 0003 | Separate ImportEvidence, RecordRevision and ImportReceipt tables preserve existing rows. Old batches and seeded records are not assigned invented source hashes or upload history. |
| Explicit correction instead of silent replacement | Append mode accepts identical rows as unchanged and rejects changed natural keys. Corrections require an existing operational key and reason; before/after revisions, optimistic comparison and the import receipt commit atomically. Corrections support sales, calendar and inventory snapshots; they do not delete rows or implement a stock movement ledger. |
| Distinguish received text from original file evidence | The API hashes the exact received UTF-8 CSV text and parsed canonical rows separately. A client-declared original file hash remains unverified; source IDs, mapping version and tenant metadata do not certify enterprise authorization. Partial parsing/validation is reported explicitly. |
| Immutable calculations with live input freshness | Jobs/results keep scoped row hashes, revisions and collection selectors. Corrections, ABA and newly relevant rows make old inputs stale. Approval of a ready plan requires verified unchanged inputs; already approved results, exports and exact idempotent replies remain historical facts. Legacy calculations without lineage need recomputation. |
| Import history follows operational read scope | Committed batches can be read by authorized roles in their current organization and every covered branch. Uncommitted previews are limited to their actor or admin; only the original actor can commit. Reimporting a pre-existing branch never grants missing branch access. |
| Empty operator-owned bootstrap | `manage_tenant.py` requires an explicit existing database with supported versions, validates metadata, defaults to preflight and gets the first admin password via hidden input on apply. No automatic demo rows, email invitations or permission for REAL data. |
| Separate tenant data policy and status | `unconfigured` allows identity/setup only; `synthetic_only` preserves the existing artificial dataset boundary. Suspend revokes sessions/refresh and pending jobs atomically; resume does not revive them. Organization → User → session/job locking serializes tenant mutations for correctness; production throughput remains unmeasured. |
| Truthful workspace onboarding | No default branch ID or fabricated organization name. Settings and authorized branches load before operational screens; the first branch CSV commit refreshes session access and branch choices without logout. Unknown metadata and absent history remain visibly empty. |
| Validated JSON operational rows | Preserve source schema/source IDs; scope and unique natural keys are indexed columns. CSV references are enforced in the import transaction, not normalized per-entity SQL foreign keys. |
| Separate durable database worker | Queue state, immutable input snapshot and result persist. No Redis/Celery dependency. Crashed job lease is 30 minutes; long tasks need heartbeats. |
| Opaque web/native auth | HttpOnly cookie + Origin/CSRF for web; short-lived access and one-use rotating refresh for native. Tokens are hashed in DB; refresh reuse revokes its family. |
| Explicit seed CLI | No embedded administrator password or automatic startup seeding. Random password printed once or read from environment. |
| Strict nine-file allowlist | Oracle, unknown fields and source generator parameters never enter operational storage, API, or training features. |
| Observed-sales target | Forecast predicts observed units_sold; does not claim recovery of unobserved demand under stockout. |
| Common temporal holdout | Models use the same 28-day test. Baselines have null quantiles; HGB intervals carry measured coverage, not an invented accuracy claim. |
| MILP with independent validation | Integer packs, MOQ, maximum supply, budget, storage and lead time are checked again using Decimal. Shortage and solver status remain visible. |
| Approval is an internal decision | Version compare-and-swap, idempotency and audit share a transaction. No supplier communication is triggered. |
| CSV export includes incomplete plans | Summary and per-ingredient requirements are exported even with zero purchase lines; users can inspect shortage. |
| Reproducible synthetic research | artifacts/research is generated by actual calculations and records code/data hashes and runtime versions. It is not evidence of field savings or interviews. |
| Strict research provenance | All six research input files must contain explicitly SYNTHETIC rows before computation or output. REAL, mixed, missing-origin and empty inputs are rejected; an alternative data directory must not silently relabel actual enterprise records. |
| Offline POS adapter with a separate REAL boundary | [Mapped aggregate sales and inventory preparation](../docs/POS_ADAPTER_RU.md) is implemented; no live enterprise connector or REAL database import is claimed. REAL remains REAL. Dry run is the default; explicit writes create a new ignored .cache/enterprise-adapter bundle, with no overwrite or source mutation. |
| Enterprise privacy and source authorization | Adapter checks reject known personal/oracle columns, unknown columns and unsupported units, but are not a comprehensive PII audit. Real sources, sensitive mappings and outputs must stay outside Git/release archives; source authorization and complete enterprise validation remain separate prerequisites. |
| Commercial stage 1 data contract | The first pilot is one branch, one agreed business timezone and KZT. A versioned discovery/data contract and POS mapping profile document the nine canonical CSVs; no real source is committed and the current operational importer remains SYNTHETIC-only. |
| Aggregate dry-run quality summary | Offline adapter reports counts/ranges/flags/units and a not-run reference-check status without exposing source IDs or values. Foreign keys, organization scope and application compatibility are checked only at a later transactional commit boundary. |
| Analyst is read-only | API and KK/RU web controls agree: only admin/manager enqueue forecasts and procurement. Import permissions are admin: all nine schemas, manager: sales/calendar/inventory, warehouse: inventory. Analyst can read permitted templates and saved results. |
| Revocation and worker publication serialize | Access updates and result publication lock the same actor row. Access updates cancel queued/running jobs with audit; publication atomically compares running status and the claim timestamp before inserting result/audit. Completed results are retained. An in-flight calculation may finish CPU work but cannot publish after cancellation. SQLite and isolated local PostgreSQL 17.11 tests cover the new lock path; deployment is separate. |
| Explicit environment validation | local remains the SQLite/HTTP demo. production requires exact HTTPS origins, secure cookies and an explicit PostgreSQL URL; demo seeding is denied. Configuration validation precedes API/worker DB access and never prints credentials. This is not tenant provisioning, REAL import or proof of TLS deployment. |
| Honest partial CSV reports | Offline quality aggregates use valid nonduplicate rows only; rows_seen/rows_checked, scan_complete and stop_reason distinguish complete scans from limits/errors. CSV header parsing is guarded in both the offline adapter and API parser. Source values are not echoed in parser errors. |
| Password lifecycle shares the actor lock | Login, refresh, password change/reset, access updates and result publication acquire User before touching sessions/jobs. Password replacement revokes all sessions, refresh tokens and pending jobs atomically and emits an audit event. Concurrent login/refresh cannot issue a session based on credentials from before the locked reset. No new schema is required. |
| Operator recovery before email infrastructure | Authenticated self-change is in web KK/RU for every role. Recovery requires an operator with DB access, exact organization/user IDs, named actor and reason; CLI defaults to preflight and accepts passwords only through hidden terminal input. It does not reactivate users or impersonate an application actor. Identity verification and secure handover remain operator responsibilities; email reset and forced first-login change are separate unfinished work. |
| Explicit PostgreSQL test fixtures | Security suites opt into an explicitly named fresh database and a separate generated schema per test. SQLite stays the default; existing stores/volumes are preserved. Local existing Docker images run read-only workspace code without pulls; reports record actual backend, source hashes and executed tests. |
