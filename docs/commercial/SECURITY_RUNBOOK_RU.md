# AsBoljam — настройки среды и действия оператора

Состояние: 29.09.2026. Эти меры можно проверить локально на синтетических организациях.
Они не подтверждают внедрение у клиента, независимый аудит или production-ready статус.
Режим среды не меняет `data_origin`: операционный importer по-прежнему принимает только
`SYNTHETIC`, а `REAL` остаётся за границей текущей реализации.

## Режимы и проверка перед запуском

`ASBOLJAM_ENV=local` — значение по умолчанию. Сохраняются локальная SQLite-база,
HTTP origins `http://localhost:3000,http://127.0.0.1:3000` и `COOKIE_SECURE=false`.
Это режим демонстрации и изолированных тестов, не инструкция публиковать API в интернете.

`ASBOLJAM_ENV=production` включает обязательную проверку перед открытием БД API/worker:

- `ALLOWED_ORIGINS` задан явно: только точные HTTPS origins. Пример безопасного
  обозначения: `https://app.example.org`. Пути, завершающий `/`, query/fragment,
  встроенные credentials, wildcard, пустые элементы и ошибочные порты запрещены.
  Регистр hostname, стандартный порт и IPv6 приводятся к форме браузерного Origin.
- `COOKIE_SECURE=true`. Значения кроме `true`/`false` являются ошибкой в обоих режимах.
- `DATABASE_URL` задан явно и выбирает PostgreSQL. Не допускаются неявная demo SQLite,
  незаданный database name и известные placeholder-пароли. Пароль внутри URL не обязателен:
  отдельная инфраструктура может использовать socket/certificate/IAM-аутентификацию.
- `DEMO_PASSWORD` отсутствует или пуст. Demo seed CLI отказывает в production до записи
  в БД. Это защита от нового seed; существующие пользователи/данные автоматически
  не анализируются и не удаляются.
- Опечатка в `ASBOLJAM_ENV` останавливает запуск; допустимы только `local` и `production`.

Секреты задаются средой или приватным secret store. Python сам не читает `.env`;
локальные launchers читают его, но также запускают demo seed и поэтому для production
не предназначены. Не переносить демонстрационную БД и demo-учётные записи в клиентскую среду.
Ошибка валидации называет переменную, не печатая URL, пароль или переданное значение.

Проверка уже установленного окружения без соединения с БД:

```text
python -m apps.api.config
```

Она проверяет синтаксис и перечисленные условия, но не проверяет доступность БД,
силу выбранного пароля, состав пользователей, сертификаты или реальную TLS-сессию.
В Compose режим передаётся API и worker; текущий Compose остаётся локальной топологией
с loopback-портами. Для внешнего запуска отдельно нужны HTTPS reverse proxy,
доверенная сеть до БД или проверяемый TLS для удалённой БД, мониторинг и проверка восстановления.

## Организация и доступ пользователей

Сейчас публичного self-service создания tenant нет. Не использовать demo seed как
регистрацию клиента. До первого пилота оператору понадобится отдельная проверяемая
процедура создания организации, первого администратора и первоначальных справочников.

Администратор создаёт пользователей своей организации через существующий раздел
пользователей, задавая роль и доступные филиалы. Сначала проверяет права на тестовом
пользователе: analyst — чтение, warehouse — складские операции, manager — расчёт и
внутреннее утверждение; управление пользователями и справочниками доступно admin.
Точные ограничения определяет API, скрытие кнопки не заменяет проверку на сервере.

При увольнении или ошибочно выданном доступе администратор отключает пользователя или
сужает его разрешённые филиалы/роль. После изменения проверить отказ старой web-сессии
и native access/refresh в изолированном тесте; история аудита остаётся доступной
уполномоченному сотруднику. Не передавать общий admin-пароль всем работникам.

Изменение доступа также атомарно помечает задания этого сотрудника в состояниях
`queued`/`running` как `failed` с кодом `JOB_ACCESS_REVOKED` и событием `job.cancelled`.
Завершённые расчёты не удаляются. Worker проверяет права перед вычислением и перед
публикацией; запись результата проверяет статус и время получения задания в одной
транзакции. Уже начатое вычисление может продолжать использовать CPU, но после отмены
его результат не сохраняется. Возврат прав не перезапускает старые задания автоматически.
Параллельные завершения и отзыв проверены на SQLite; новую блокировку на PostgreSQL
нужно проверить отдельно. Длительным задачам свыше текущей 30-минутной аренды всё ещё
нужен heartbeat; защита от устаревшего worker предотвращает повторную публикацию.

## Резервирование и восстановление

Локальную SQLite копировать штатным `scripts/backup_db.py`, а не копированием активного
файла вместе с WAL вручную. Восстановление выполнять в новый путь, сохраняя исходную БД.
Команды и ограничения приведены в корневом README.

Для PostgreSQL использовать подходящие версии `pg_dump`/`pg_restore`; credentials
передавать через защищённый механизм среды, без записи в Git или журнал команды.
Проверять восстановление в отдельную БД: миграции, количество записей, вход и рабочий
сценарий. Имеющийся локальный Docker restore не доказывает восстановимость будущей
клиентской инфраструктуры. Периодичность, срок хранения, RPO/RTO и шифрование backup
нужно согласовать до пилота; реальные backup не включаются в source ZIP.

## Подозрение на утечку сессии

1. Отключить затронутого пользователя через admin API/UI и проверить отзыв его сессий.
2. Сохранить идентификаторы инцидента и события аудита без cookies, токенов и паролей.
3. Определить доступные скомпрометированному пользователю организацию/филиалы и период.
4. Восстановить доступ после проверки причины и замены затронутых секретов. Смена
   пароля/reset flow пока не реализованы в UI; не выдавать старый пароль повторно.

Смена PostgreSQL credential или восстановление доступа единственного администратора
требуют отдельного операторского действия. Фактическое реагирование и оповещение
владельца бизнеса ещё не проверены, пока нет реального пилота и договорённостей.

## Удаление организации

Автоматического удаления tenant пока нет. До реализации процедуры нельзя обещать
удаление нажатием кнопки. Нужны подтверждённая область организации, согласованный
срок хранения, учёт operational rows/jobs/import previews/sessions/audit и backup,
отзыв доступов и проверяемый результат. Не удалять общие таблицы или Docker volumes
для удаления одного клиента. Реальные сроки и условия определяет договор данных;
в текущем этапе не выполняется удаление пользовательских данных.
