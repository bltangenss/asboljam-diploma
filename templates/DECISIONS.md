# Decisions — 2026-09-24

| Decision | Reason and consequence |
|---|---|
| Day factors enter a fourth model, never the history models | Twenty factors (apps/api/factors.py): seventeen imported through the optional `day_factors` schema (date, branch, code, value), three derived from daily_sales (price ratio, planned promo, past-week stockout share). Every factor is read for the same day in training and on the forecast day, so only values known before that day are allowed (weather is a forecast). A factor is used only with a target-day value and ≥90% training coverage; otherwise it is skipped with a reason. Target-day price is the last known price and missing promo plans mean no promotion; both assumptions are stored in the result. The three history models, their metrics and scripts/run_research.py are unchanged; the factor model is evaluated on the same 28-day test only when the branch has usable factors. Runs that read factors capture them in input_lineage; earlier runs do not become stale when factors are first imported. The KZ demo factors are deterministic (official calendars, DUMK, Ministry of Education orders, astronomy); precipitation, trains and office occupancy have no demo data rather than invented series. |
| Each establishment works in its own cabinet | A branch account (role manager, exactly one branch) signs in straight to its establishment: the header shows its name, there is no branch selector, and every request stays scoped by the existing API branch checks. Only an organization account with several branches switches cabinets, from the same place in the header. The local demo seed adds one such sign-in per branch (`branch-<id>@asboljam.local`, same demo password, existing accounts untouched, `--no-branch-accounts` to skip). No new role, migration or permission rule. |
| Header day flow, sheets instead of side columns (Oct 2026) | The four steps of the working day (Today, day plan, stock, purchase) are the header navigation; data/analysis and settings are header tools; Ctrl+K opens a command palette. No permanent left rail on desktop (it remains the compact-screen drawer). Secondary material — history, past runs, evidence, technical details, supplier prices, chart/metrics — opens as a sheet from a chip row under the title instead of a right column or a stack of accordions. Calculations are one composer row; approval is a sticky decision bar. Today orders attention (focus step + remaining tasks) → four steps with state and actions → last known day. Counted stock is an ingredient shelf (units never merged, expired lots shown but not counted) with the lot table one switch away. Routes, roles, API and decision rules are unchanged. |
| Immutable cooking variants separate from forecasts | Manager/admin explicitly saves named integer portions for every forecast meal with reason, actor and idempotent receipt. Variants never overwrite forecasts, automatically become the day head, post stock or approve purchases. Procurement may bind an exact variant with point strategy; p50/p90 remain forecast-only. Original forecast and context are retained for worker fencing, while manual demand is derived separately. Frozen evidence and conditional CSV columns preserve older approved exports. Migration0009 adds two empty tables. |
| Daily-task information architecture | Five primary groups: Today, day plan, stock, purchases, data/analysis; settings/audit are secondary. Stable routes remain usable. Today prioritizes actionable warnings, then work, then analytics. Forecast portions are a cooking reference, not a persisted production plan. Stock task panels remain mounted to preserve uncertain command retries; technical history is disclosed. Related reference detours and CSV remediation preserve scoped calculation context. Approval remains an explicit versioned human decision. |

Next steps derive from actual dates, input freshness and decision status, never fabricated readiness. Technical evidence is disclosed without hiding deficits or uncertain mutation outcomes. System fonts support KK/RU without external font requests. |
| Kazakhstan demo is a second reproducible SYNTHETIC dataset | The product demo must look and behave like a Kazakhstan business, while the supplied diploma dataset keeps its research results and test expectations. `data/kz` (Qyzylorda: Kazakh dishes, KK/RU ingredient names, 2025 KZT price levels, official RK days off and transfers 2024-2025, Ramadan, climate) is generated by `scripts/generate_kz_demo.py` with stdlib sampling and a byte-for-byte regeneration test. The seed CLI defaults to `kz`; `seed()` used by tests/fixtures and `run_research.py` default to `data/raw`. Same nine schemas and dates; public facts only shape the scenario and are cited in `data/kz/README.md`. An existing database keeps its dataset (the seed warns, never deletes). The forecast still ignores the calendar, so RK holidays are a documented limitation pending an owner decision. |
| Counted snapshots remain independent of the stock journal | Opening(E) includes only movements before E. An opened journal must reconcile with the exact target count for procurement. Missing lots remain unknown. Approval never posts stock or sends a supplier order. |
| Dated recipes are explicit complete decisions | Migration0007 stores branch/meal activations separately from the nine CSV schemas. Freeze each recipe row's unit and yield. If any selected forecast meal uses dated recipes, require complete activation coverage; no partial silent fallback. |
| Frozen evidence and period-scoped freshness | Capture journal opening, relevant earlier movements and effective recipe selections with each plan. Future documents do not stale old targets. Relevant changes block new approval; stored results, approved exports and idempotent decision receipts remain immutable. |
| Baseline correction uses an explicit immutable count anchor | Migration0008 preserves the original baseline and movements. Admin/manager reviews a complete independently counted snapshot, reason and disclosed differences, with strict acknowledgement, expected version/fingerprint, idempotency and audit. Missing known lots require explicit zero; changed source identity remains blocked. |
| Count anchors close their preceding movement boundary | An anchor date is after every posted movement and earlier anchor; the first may equal the original baseline only with no movements. Movement sequence and journal version are separate. Replay selects the anchor for the requested period; no reversal may cross its movement watermark. Correcting an accepted count needs a later independent count, not in-place editing or same-date replacement. |
| Server-owned request correlation, commit-ordered diagnostics | The outermost middleware generates X-Request-ID and logs only fixed method, registered route template, status, duration and fixed failure codes. Middleware order is correlation -> CORS -> protection so early refusals and the generated 500 are readable by allowed origins. Job events are emitted only after the matching commit; rollback/CAS loss are logged as discarded or publication_error, never success. Unhandled exceptions reach the ASGI server only as RuntimeError HTTP_REQUEST_FAILED without the original chain. Uvicorn access logs are disabled because they record raw paths and queries. Logs are best-effort stdout diagnostics, not audit; no new schema or telemetry provider. |
