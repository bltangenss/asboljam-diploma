# AsBoljam — прогноз продаж, склад и закупки для общепита

> Контекст продукта и инструкция продолжения для разработчика, Claude Code или другого coding agent.
> Состояние сверено с кодом, Git и сохранёнными отчётами **11.10.2026**. Продолжайте существующий проект, не создавайте замену.

AsBoljam помогает владельцу кафе, столовой или фастфуда понять, **сколько порций может быть продано в следующий расчётный день, сколько сырья потребуется, сколько пригодного сырья уже есть и какие упаковки стоит закупить в рамках бюджета**. Решение принимает человек. Система сохраняет основания расчёта, ограничения, решение менеджера и аудит.

Проект начинался как дипломная работа и развивается в сторону коммерческого продукта для Казахстана. Рабочие web/API, воспроизводимые вычисления, импорт, складской журнал и клиент Expo уже существуют. **Реальный бизнес-пилот и production deployment пока не подтверждены.**

## 2. Продукт простыми словами

### 2.1. Зачем фастфуду AsBoljam

Владелец знает, что вчера продал 80 бургеров. Закупка на расчётный день зависит от ожидаемых продаж, состава блюд, потерь сырья при подготовке, остатков, сроков годности, размеров упаковок, цен и бюджета. Программа связывает эти части в один процесс:

```text
Ежедневные продажи по блюдам
  → прогноз порций на следующий день после закрытой истории
  → рецептуры + выход сырья → потребность в ингредиентах
  → точный пригодный остаток + сверка складского журнала
  → предложения поставщиков + упаковки + ограничения + бюджет
  → план закупки, стоимость, нехватка и предупреждения
  → решение менеджера → аудит → CSV
```

Условный пример: прогноз 100 бургеров, в рецепте 0.12 kg нетто мяса, выход 0.8. Брутто-потребность `100 × 0.12 / 0.8 = 15kg`. Есть 5 kg пригодного остатка, купить нужно 10 kg. При упаковке 2 kg и цене 2000 KZT заkg это 5 упаковок стоимостью `5 × 2 × 2000 = 20000KZT`, если прочие ограничения позволяют.

Это объясняющий пример, не измерение предприятия и не обещание экономии. При недостаточном бюджете программа покажет непокрытую потребность. Менеджер должен увидеть дефицит и осознанно решить, что делать.

### 2.2. Повседневный сценарий

1. Администратор создаёт организацию и сотрудников с доступом к филиалу.
2. Загружаются справочники блюд, ингредиентов, рецептур, поставщиков и предложений.
3. Загружаются история продаж и независимый посчитанный остаток.
4. Менеджер выбирает филиал, завершённый день истории и модель.
5. Worker рассчитывает прогноз; UI показывает статус, результат и метрики.
6. Менеджер выбирает бюджет и стратегию закупки.
7. Система переводит порции в сырьё, вычитает годный запас и подбирает упаковки.
8. Менеджер изучает дефицит и основания, затем утверждает/отклоняет план с причиной.
9. Решение сохраняется в аудите, план выгружается в CSV.
10. Фактические приходы, списания, расход и пересчёты вводятся отдельными документами.

Продажи CSV сами по себе не списывают склад. Утверждение плана не создаёт приход, не переводит деньги и не отправляет заказ поставщику.

### 2.3. Чего пока нет

- Подтверждённой точности/экономии на настоящем предприятии.
- Готового live-коннектора iiko, r_keeper, Poster, 1 С или другой POS. Есть офлайн CSV-адаптер.
- Действующего биллинга, банковских платежей, публичного self-service SaaS onboarding.
- Полного бухучёта, налоговой отчётности или ERP.
- Восстановления скрытого спроса при stockout.
- Подтверждённого production SLA, нагрузочной ёмкости и отказоустойчивости кластера.
- Многодневного пополнения с полноценной будущей логистикой: текущий горизонт — один день.

## 4. Данные и девять CSV

### 4.1. Режимы данных

| Политика / происхождение | Значение | Ограничения |
| --- | --- | --- |
| `unconfigured` | Организация есть, операционная политика не настроена | Данные и расчёты недоступны |
| `synthetic_only`, `SYNTHETIC`, `DEMO` | Учебная демонстрация | История до **2025-12-31**, цель/исходный остаток **2026-01-01** |
| `real_only`, `REAL`, `TEST` | Проверка REAL-контракта на явно сгенерированном наборе | Не является данными предприятия |
| `real_only`, `REAL`, `PILOT` | Протокол согласованного пилотного источника | Завершённый бизнес-день, timezone, происхождение и разрешение оператора |

`REAL` на искусственной TEST-fixture не доказывает подлинность бизнес-источника. Назначение TEST должно быть видимо. Регистрация PILOT оператором не заменяет согласование и проверку выгрузки.

В одной организации нельзя смешивать REAL/SYNTHETIC. Заполненное demo нельзя переключить в REAL. Источник регистрируется отдельно в пустой организации. Текущий REAL-протокол — **один источник и один филиал на организацию**; synthetic demo содержит три филиала. Несколько REAL-филиалов, консолидация сети и межфилиальные перемещения требуют следующей разработки.

### 4.2. Формат и точные схемы

- CSV с запятой, UTF-8; BOM принимается.
- Дата `YYYY-MM-DD`, десятичный разделитель точка.
- ID — строки: `001` не превращать в число `1`.
- Денежные и физические величины сохраняются десятичными строками.
- Текущие единицы сырья: **`kg` и `L`**. Штуки, граммы и миллилитры не поддержаны как самостоятельные единицы; преобразование требует согласованного правила.
- `data_origin` обязателен и совпадает с политикой организации.
- Неизвестность не подменяется нулём. Флаги доступности/stockout/открытия/промо нельзя угадывать ради прохождения импорта.
- Для задачи нужны агрегированные операционные данные, не телефоны клиентов, ФИО, карточные данные или чеки с персональными сведениями.

Источник истины: [apps/api/importing.py](apps/api/importing.py), `SCHEMAS`/`KEYS`. Описание: [contracts/data_manifest.json](contracts/data_manifest.json).

| Файл / kind | Назначение | Обязательные столбцы |
| --- | --- | --- |
| `branches.csv` | Филиалы | `branch_id,branch_name,data_origin` |
| `meals.csv` | Меню | `meal_id,meal_name,base_price_kzt,data_origin` |
| `ingredients.csv` | Сырьё, выход, вместимость | `ingredient_id,ingredient_name,unit,reference_cost_kzt,shelf_life_days,yield_factor,storage_capacity,data_origin` |
| `recipes.csv` | Нетто на порцию | `meal_id,ingredient_id,net_qty_per_portion,recipe_version,data_origin` |
| `suppliers.csv` | Поставщики | `supplier_id,supplier_name,lead_time_days,data_origin` |
| `supplier_offers.csv` | Упаковки, цена базовой единицы и лимиты | `supplier_id,ingredient_id,pack_qty,unit_cost_kzt,min_packs,max_packs,lead_time_days,data_origin` |
| `calendar.csv` | Контекст дня | `date,branch_id,weekday,temperature_forecast_c,synthetic_event,is_open,data_origin` |
| `daily_sales.csv` | Продажи блюда за день | `date,branch_id,meal_id,units_sold,available_portions,stockout_flag,is_open,promo,price_kzt,data_origin` |
| `inventory_lots.csv` | Посчитанный остаток по партиям на дату | `branch_id,ingredient_id,lot_id,snapshot_date,expiry_date,on_hand_qty,unit,data_origin` |

Порядок столбцов может отличаться, обязательный набор — нет. У предоставленного SYNTHETIC-набора есть узкое исключение: `demand_multiplier` у филиалов и `base_daily_demand` у блюд отбрасываются на границе импорта. Они не используются в обучении; REAL не получает разрешения импортировать генераторные поля.

Естественные ключи:

- Справочник филиалов/блюд/ингредиентов/поставщиков: собственный ID.
- Рецепт: `meal_id + ingredient_id + recipe_version`.
- Предложение: `supplier_id + ingredient_id`.
- Календарь: `date + branch_id`.
- Продажа: `date + branch_id + meal_id`.
- Остаток: `branch_id + ingredient_id + lot_id + snapshot_date`.

### 4.3. Что подготовить фастфуду

Прогноз требует **минимум 84 непрерывных дня на каждое включённое блюдо до origin включительно**. Проверяется непрерывность имеющейся серии, а не только наличие любых 84 строк. Пропущенный день не дописывается нулём. Если фактически день закрыт или продаж не было, нужна соответствующая достоверная строка и корректные флаги.

**Текущая граница REAL-дат:** origin должен быть строго раньше сегодняшнего бизнес-дня в timezone организации; target равен origin + 1. Например, если в организации сегодня 11.10.2026, последний допустимый origin — 10.10.2026, цель — 11.10.2026. Обычный сценарий: закрытые вчерашние продажи → план сегодняшнего дня. Исторические расчёты разрешены; расчёт на будущую календарную дату 12.10.2026 при таком текущем дне пока не поддержан. Полноценное планирование «на завтра» до закрытия сегодняшнего дня требует отдельного контракта и доработки, а не обхода проверки даты.

Для закупки нужны полные рецептуры, ингредиенты с yield/единицами, предложения и срез остатков **точно на target date**. В REAL требуется полнота нужных ингредиентов. При действительном отсутствии сырья указывается явный ноль; отсутствие строки означает неизвестность и может блокировать расчёт.

Загружайте сначала `branches`, затем справочники `meals`, `ingredients`, `suppliers`; после них зависимые `recipes`, `supplier_offers`, `calendar`, `daily_sales`, `inventory_lots`. Ссылки должны существовать в той же организации. Первый REAL-филиал совпадает с зарегистрированным `branch_id`.

Шаблоны — на странице импорта и в разрешённом `GET /api/v1/imports/template/{kind}`. Не каждая роль может получить все девять видов шаблонов.

### 4.4. Импорт, повтор и исправление

Процесс: файл → preview/ошибки → просмотр → отдельный commit.

- Плохая строка не должна приводить к частичному изменению операционных данных.
- `append` добавляет новые ключи; идентичные старые строки остаются неизменными.
- Изменение существующего ключа требует `correction`, причины и просмотра «было → стало».
- Corrections поддержаны для продаж, календаря и срезов остатков.
- Повтор с тем же idempotency key и телом возвращает сохранённый результат, не создавая второй эффект.
- История хранит актёра, scope, источник, хеш принятого CSV-текста и канонических строк.
- Заявленный клиентом хеш исходного файла не является независимо проверенным доказательством.
- Старые данные без происхождения остаются неизвестными; им не присваивается вымышленная история.
- Отчётный CSV с метаданными не обязан быть файлом для обратного импорта.

Офлайн `scripts/adapt_pos_csv.py` преобразует согласованную POS-выгрузку. По умолчанию dry run; он не пишет в БД и не подключается к кассе. Проверки ссылок, прав и commit проходят отдельно в API. См. [POS_ADAPTER_RU.md](docs/POS_ADAPTER_RU.md), [IMPORT_OPERATIONS_RU.md](docs/commercial/IMPORT_OPERATIONS_RU.md).

## 5. Прогноз и обучение модели

### 5.1. На чём прогнозируется

**Сейчас модель использует observed `units_sold`, выбранный филиал, блюдо и признаки даты.** Склад, рецептура и поставщики используются позже для закупки, не как признаки прогнозной модели.

Реальные признаки из `apps/api/engine.py`:

```text
meal_category
day_of_week, month
lag_1, lag_7, lag_14, lag_28
rolling_mean_7, rolling_mean_28
rolling_std_7, rolling_std_28
```

`meal_category` — внутренний категориальный код блюда в выбранном филиале, не внешняя классификация кухни. Лаги/скользящие признаки берут строго прошлые наблюдения относительно предсказываемого дня.

**Погода, промо, цена, `synthetic_event`, `available_portions`, `stockout_flag` сейчас не являются входными признаками обучения.** Наличие столбца в CSV не означает, что модель уже учитывает его влияние. Поля сохраняются/проверяются для контекста и аудита. Новые признаки требуют доказательства доступности на момент прогноза, временного теста и защиты от утечки будущего.

Цель — наблюдённые продажи, не скрытый спрос. Если блюдо закончилось в 14:00, продажи могут быть ниже истинной потребности клиентов. Текущая модель автоматически не восстанавливает непроданные порции.

### 5.2. Модели

| Идентификатор | Принцип | Квантили |
| --- | --- | --- |
| `seasonal_naive_7` | Продажи соответствующего дня неделю назад | p10/p50/p90 = null |
| `rolling_mean_28` | Среднее последних 28 дней | p10/p50/p90 = null |
| `hist_gradient_boosting` | HGB по прошлым продажам и признакам даты | Point и отдельные p10/p50/p90 |

HGB **реально обучается во время расчёта**. Это не универсальные готовые веса, обученные на казахстанских ресторанах, и не LLM/API-вызов. Сохраняются результаты и метаданные; централизованный model registry и отдельный production training pipeline не заявлены готовыми.

Для оценки HGB обучается на истории до тестового периода. Для финального HGB-прогноза переобучается на доступной истории до origin. Baselines отдельного такого fit не требуют. Общая сравнительная оценка считает все три модели даже при выборе baseline для итогового прогноза.

Текущие параметры: seed 42, `max_iter=70`, `max_leaf_nodes=15`, `learning_rate=0.08`, `min_samples_leaf=15`, `early_stopping=False`. Это текущая реализация, не доказанный оптимум для ресторана.

### 5.3. Проверка качества и ограничения

- Горизонт один день: `target_date = origin + 1 день`.
- В REAL origin — только завершённый день до текущего бизнес-дня; ближайшая разрешённая цель — сегодняшний день. «Следующий день» здесь отсчитывается от origin, не от часов компьютера.
- Все модели сравниваются на общем тесте последних 28 дней.
- Это последовательные однодневные прогнозы: ранее наблюдавшийся тестовый день может стать прошлым лагом следующего; HGB не переобучается на тестовом периоде для этой оценки.
- Метрики: MAE, RMSE, WAPE, bias, эмпирическое покрытие интервала и исходная доля пересечений квантилей.
- При нулевой сумме тестовых продаж WAPE = null, не выдуманные 0%/100%.
- p10–p90 — **номинальный 80% интервал**, не «90% точности».
- Отрицательные прогнозы ограничены нулём, квантили упорядочены; исходная доля crossing сохранена.
- Сохраняются seed, features, data hash, runtime versions, train/test dates, время вычисления.

Никогда не использовать для обучения `research_only`, `oracle_do_not_train.csv`, `latent_demand_ORACLE_ONLY`, `demand_multiplier`, `base_daily_demand`, будущие факты или same-day audit-only поля, даже если это улучшает метрику.

### 5.4. Что уже измерено

Предоставленная synthetic-демонстрация: 26316 продаж, 3 филиала, 12 блюд, 10 ингредиентов, 48 строк рецептов, 30 предложений. Сохранены 9 прогнозов и 36 закупочных сценариев. HGB WAPE на трёх искусственных филиалах примерно 22.50%, 25.65%, 24.46%.

Это характеристики конкретного синтетического исследования, **не качества реального фастфуда**. См. [artifacts/research/README_KK.md](artifacts/research/README_KK.md). `python scripts/run_research.py` воспроизводит исследование; его не нужно повторять после изменения только README.

<a id="procurement"></a>
## 6. Расчёт закупки

### 6.1. Порции → сырьё → упаковки

```text
брутто = сумма(порции × net_qty_per_portion / yield_factor)
к закупке = max(0, брутто − пригодный остаток)
стоимость строки = packs × pack_qty × unit_cost_kzt
```

Yield применяется **ровно один раз**. `unit_cost_kzt` — цена базовой единицы kg/L, не автоматически цена упаковки. Остаток берётся только из среза точной целевой даты, из непросроченных партий. В текущем правиле срок в саму целевую дату ещё пригоден.

### 6.2. Оптимизация

`scipy.optimize.milp` сначала минимизирует относительный дефицит, затем стоимость в рамках решения первой цели. Учитываются целые неотрицательные упаковки, MOQ при использовании предложения, max packs, бюджет, вместимость по ингредиенту, годный остаток и zero-day lead time предложения.

После solver ограничения независимо перепроверяются с Decimal. `optimal` не означает отсутствие дефицита. Нулевой бюджет допустим, непокрытая потребность показывается даже при пустом списке закупок. Kg/L не складываются в одну физическую сумму.

Стратегии: `point` для всех моделей, `p50` и `p90_stress` для HGB. Сумма p90 блюд — **стрессовая эвристика**, не совместная гарантия 90% уровня обслуживания.

### 6.3. Решение и история

Утверждение/отклонение проверяет актуальные права, scope, ожидаемую версию, причину, idempotency и отдельное подтверждение дефицита. Решение и audit атомарны. Новый approve устаревшего/непроверенного плана требует пересчёта.

Уже утверждённый результат и export — исторический факт: изменение справочника не пересчитывает его при чтении. Повтор того же решения возвращает прежний ответ. Утверждение не создаёт внешний заказ.

<a id="stock"></a>
## 7. Склад, рецепты и пересчёты

### 7.1. Срез и журнал — разные источники

`inventory_lots.csv` — независимо посчитанный срез. Журнал — последовательность явно проведённых документов от исходной основы. Система сверяет их, а не скрыто приравнивает один к другому.

Начало дня E включает движения до E; движения самого дня E не входят в его начальный остаток. После открытия журнала закупке нужен точный целевой срез, совпадающий с журналом. Отсутствующая сторона остаётся неизвестной.

### 7.2. Документы

- Открытие по полному посчитанному срезу с причиной.
- `receipt` — приход в конкретную партию.
- `waste` — списание.
- `recipe_usage` — расход по приготовленным порциям и полному датированному рецепту.
- `adjustment` — явная корректировка.
- `reversal` — обратная запись, когда допускает граница периода.
- `count_anchor` — принятие нового полного посчитанного остатка.

Проведение: preview, version/fingerprint, необходимые подтверждения, idempotency и audit. Одна плохая строка отменяет документ. Проведённые документы не редактируются/не удаляются.

Количества — decimal strings до девяти дробных знаков. Отрицательный остаток запрещён. Единица/expiry существующей партии не меняется незаметно. Просроченное можно списать, но нельзя принять как годное или расходовать по рецепту.

Recipe usage требует точного распределения брутто по партиям. Дроби суммируются по ингредиенту и округляются вверх до `10^-9` kg/L; правило сохраняется в свидетельстве. Продажи автоматически такое списание не создают.

### 7.3. Датированные рецептуры

CSV `recipe_version` и датированная активация — разные механизмы. Legacy CSV ограничен одной активной версией; новую активацию проводят через специальный API/UI.

Активация фиксирует полный состав блюда, филиал, дату, нетто, единицы и yield каждой строки. Если хотя бы одно прогнозируемое блюдо использует активированные рецепты, полные активные рецепты нужны всем блюдам прогноза. Нельзя тихо смешать неполный новый состав с legacy fallback или переписать уже проведённый расход.

### 7.4. Принятый пересчёт (`count_anchor`)

Механизм **реализован и проверен**. Он позволяет принять исправленный посчитанный остаток без переписывания прежней истории:

1. Импортировать точный полный срез.
2. Manager/admin выбирает дату, пишет причину, видит прежнее/новое количество и каждую разницу.
3. Явно подтверждает расхождения и принятие.
4. Сохраняется неизменяемый документ, источник, автор, прежний fingerprint и граница движений.
5. Новый период использует новую основу, старые даты — свою прежнюю.

Ограничения:

- Все известные партии присутствуют, включая явный ноль; пропуск блокирует принятие.
- Найденная новая партия имеет неизвестное прежнее количество, не придуманную разницу с нулём.
- Нельзя менять единицу/expiry существующей партии или source identity REAL.
- Дата позже последнего проведённого дня и предыдущего пересчёта. Первый может совпасть с исходной датой только без движений.
- Второй пересчёт на ту же дату не поддерживается; нужен последующий независимый срез.
- Reversal не пересекает границу принятого пересчёта; используйте допустимую новую корректировку.
- Версия журнала, sequence движений и sequence пересчётов различаются.
- Поздний пересчёт не делает автоматически устаревшим план раннего периода.

См. [STOCK_LEDGER_DESIGN_RU.md](docs/commercial/STOCK_LEDGER_DESIGN_RU.md) и [STOCK_BROWSER_TEST_RU.md](docs/commercial/STOCK_BROWSER_TEST_RU.md).

### 8.2. Сессии и отзыв доступа

Web использует HttpOnly session cookie; mutations проверяют Origin и CSRF. Секреты не помещаются в localStorage. Native access token хранится в памяти, rotating refresh — в Expo SecureStore. Повтор refresh отзывает его семейство. Клиент защищён от конкурентных refresh/logout и не отправляет прежний токен другому API URL.

Изменение прав, suspend организации и смена/reset пароля отзывают соответствующие сессии и queued/running jobs. Resume не оживляет прежние токены/задачи. Worker перепроверяет право публикации в транзакции.

REAL operational native маршруты явно закрыты: `403 NATIVE_REAL_UNSUPPORTED`. Не снимать ограничение до поддержки source/date contract клиентом.

### 8.3. Пароли и оператор

Demo admin пароль не зашит. Seed печатает случайный пароль один раз или принимает приватный `DEMO_PASSWORD` от 12 символов. Повторный seed сохраняет существующий пароль. Не добавляйте его в README/Git/ZIP/логи.

Забытый пароль восстанавливает оператор через `scripts/manage_password.py`: явная БД, точные org/user, причина, скрытый ввод. Проверка личности и передача доступа — ответственность оператора. Email reset, приглашения и forced first-login change не объявлены готовыми.

Администратор организации и оператор с доступом к БД — разные роли. См. [SECURITY_RUNBOOK_RU.md](docs/commercial/SECURITY_RUNBOOK_RU.md), [TENANT_OPERATIONS_RU.md](docs/commercial/TENANT_OPERATIONS_RU.md).

## 10. Worker и диагностика

API сохраняет job и immutable snapshot, worker считает отдельно. Закрытие вкладки не удаляет job. История открывает прежний run_id без нового POST.

Worker атомарно захватывает queued job. `started_at` — идентификатор захвата; `heartbeat_at` обновляется отдельной транзакцией примерно каждые 30 секунд. Lease —30 минут. После истечения возможен новый claim; старый исполнитель не публикует результат без совпадения статуса и исходного claim timestamp.

Расчёт идёт в дочернем Python-процессе со snapshot и минимальным окружением, без переменных БД/паролей. Deadline `WORKER_CALCULATION_TIMEOUT_SECONDS` от 1 до 3600, default 900. Он не ограничивает отдельно ожидание БД при публикации.

SQLite BUSY/LOCKED повторяет короткую операцию, сохраняя уже рассчитанный результат. Другие DB faults не считаются успехом. Перед публикацией перепроверяются scope, доступ, claim и source context. Первый штатный сигнал останавливает новые claims и даёт текущему завершиться; hard kill/failover — отдельные границы.

Коды ошибок: `JOB_ACCESS_REVOKED`, `JOB_SCOPE_INVALID`, `JOB_INPUT_INVALID`, `JOB_CALCULATION_FAILED`, `JOB_TIMEOUT`. UI показывает их на KK/RU. Heartbeat — связь с БД, **не процент готовности**.

См. [WORKER_OPERATIONS_RU.md](docs/commercial/WORKER_OPERATIONS_RU.md), раздел «Диагностика request → job». Цепочка: `X-Request-ID` ответа → `job.queued` (после commit) → `job.claimed` → `job.finished`/`job.discarded`/`job.released`/`job.lease_expired`. Логи — best effort в stdout, не audit; в них нет payload/CSV/password/cookie/token/user reason/raw path/query/текста исключений БД. Хранение и ротацию логов настраивает оператор целевой среды.

### 15.1. P0 — request → job диагностика (DONE 11.10.2026)
<a id="observability-next"></a>

Выполнено и проверено; свидетельство — [request-logging-20261011.json](artifacts/verification/request-logging-20261011.json), правила эксплуатации — [WORKER_OPERATIONS_RU.md](docs/commercial/WORKER_OPERATIONS_RU.md). Ниже сохранены исходные критерии приёмки:

1. Server-generated `X-Request-ID`, входной ID полностью игнорируется, параллельные запросы не смешиваются.
2. `http.request`: только ID, fixed method, registered route template/unmatched, status, duration. Без raw path/query/body/headers.
3. Проверить early 400/413,401/403,422,404/405,500.
4. До заголовков — safe 500/security headers. После заголовков — не слать второй ответ; сохранить отправленный status и отдельно обозначить `HTTP_REQUEST_FAILED`.
5. Расширить/сверить allowlist emitter для фиксированного HTTP failure code. Стандартный ASGI traceback не должен содержать исходный exception/chain с SQL parameters, CSV или секретами.
6. Allowed origin получает доступ к X-Request-ID, включая middleware 500; чужой origin не получает CORS-разрешение.
7. `job.queued` только после успешного commit. ID/kind сохранить примитивами до commit, не добавлять ORM-read ради логирования.
8. `job.claimed`, `job.finished`, `job.released` только после соответствующего commit. CAS loser — discarded; rollback/ошибка публикации не изображаются успехом.
9. Timeout/access revoke/calculation failure/missing job/reclaim/contention имеют безопасные коды. Retry не переобучает и не дублирует terminal success.
10. Write/flush failure логов не меняет committed бизнес-результат. Stream best effort, не durable audit и не гарантия межпроцессной доставки/retention.
11. Завершить `tests/test_request_logging.py`, выполнить 18 worker tests и связанные API/security/worker suites. Неизвестный исход прежнего запуска не считать PASS.
12. Проверить `--no-access-log` launchers/Docker и безопасный Nginx access format. Syntax check не равен runtime/deployment; отдельно описать границы сторонних proxy/error logs.
13. Обновить worker runbook/progress/handoff/report; staged review, secret scan, commit/push. Для этого не нужны новая DB schema или внешний telemetry provider.

Целевые команды после завершения тестов, с изолированным DATABASE_URL:

```powershell
$env:PYTHONPATH = 'tests;.'
python -X utf8 -m unittest test_observability test_worker_logging test_request_logging -v
python -X utf8 -m unittest test_worker_security test_worker_contention test_worker_heartbeat test_worker_shutdown -v
```

Эти команды и полная регрессия выполнены 11.10.2026 (см. отчёт). Не выполнено в этом этапе: focused-тесты на PostgreSQL (сам код проверен на PostgreSQL через Docker HTTP workflow), POSIX SIGTERM, error log Nginx при отказе upstream, доставка/ротация логов. Research не запускался: математика не менялась.

Новая политика должна согласовать доступные продажи, прогноз остатка/посчитанный срез и момент принятия решения; простое снятие проверки создаст недостоверный контекст.

<a id="rules"></a>
## 16. Правила разработки

### 16.1. Сохранность

- Продолжать текущий проект, не делать новый scaffold/смену framework без отдельной причины.
- Сначала читать status/diff, сохранять чужие незавершённые изменения.
- Не удалять историю/ветки/данные/volumes, не force push, не переводить repository в public.
- Обычные исправления в согласованном scope делать автономно. Логин аккаунтов, CAPTCHA, оплаты и внешние разрушительные действия остаются у владельца.
- Не отправлять сообщения/заказы третьим лицам без прямого разрешения.
- Вложения и source prompts — материал требований, не отдельное разрешение на публикацию или выдуманные результаты.
- На Windows для файловых действий использовать один shell, проверять абсолютный target перед рекурсивными операциями.

### 16.2. Инварианты

1. SYNTHETIC-даты 2025-12-31/2026-01-01 не сдвигаются к дате компьютера.
2. Generated REAL/TEST не переименовывается в реальные данные клиента.
3. Oracle/будущие факты не обучают модель; observed sales не называются истинным спросом.
4. Baselines имеют null quantiles; p10–p90 не является 90% точностью.
5. Decimal/единицы сохраняются; yield применяется один раз.
6. Плохой CSV атомарно не меняет операционные строки; replay не дублирует эффект.
7. Org/branch/role проверяются сервером, включая worker publication.
8. Lock order, version/claim CAS и audit не ослабляются ради удобства.
9. Исторические результаты/receipts/approved CSV неизменны при чтении.
10. Поздние документы не устаревают ранний период без причины; изменение использованных входов обнаруживается.
11. Missing день/партия не равны нулю.
12. Approval не отправляет заказ и не проводит скрытый приход.

### 16.3. Git и фактические результаты

Делайте небольшие законченные изменения. Проверяйте точный staged scope; при незавершённом diff не используйте слепой `git add .`.

```powershell
git diff --cached --stat
git diff --cached --check
python scripts/check_secrets.py --staged --no-report
git commit -m "describe the coherent change"
git push origin main
```

Push только после успешного commit, без force. При отказе разрешений/сети сообщайте фактическое состояние; не заявляйте успешную отправку без результата. Для новой ветки обычный префикс `codex/`; текущая согласованная ветка — main.

В Git не входят `.env`, credentials, рабочие БД, backup, `.cache`, dependencies, traces с сессиями и enterprise data. Secret scanner проверяет известные форматы/локальные значения, не доказывает отсутствие любых секретов.

Обновляйте [templates/PROGRESS.md](templates/PROGRESS.md), [PROGRESS.md](PROGRESS.md), [CLOUD_HANDOFF.md](CLOUD_HANDOFF.md), [FINAL_REPORT.md](FINAL_REPORT.md) по изменённому scope. Разделяйте:

- **DONE** — законченная реализация.
- **IN PROGRESS** — начатый незакрытый участок.
- **TODO** — следующий объём.
- **TESTED** — реально выполненные команды и результат.
- **NOT TESTED** — непроверенная область.
- **BLOCKED** — конкретная внешняя зависимость.

В итогах указывайте commit/hash, push и реальные пути артефактов. Неуспешный тест сохраняйте в истории, удачный повтор записывайте отдельно. Не повторяйте дорогие проверки без причины и не выдавайте code review за runtime-test.

<a id="troubleshooting"></a>
## 17. Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| Job навсегда queued | Отдельный worker, совпадение БД API/worker, активный доступ |
| Ready зелёный, расчёт не идёт | Readiness не проверяет worker или качество данных |
| 401 после изменения пароля/прав | Старые сессии отозваны; повторный вход ожидаем |
| 403 | Role/branch/Origin/CSRF/tenant policy; native REAL имеет явное ограничение |
| 409 | Version/fingerprint или другой payload с тем же ключом; обновить и просмотреть, не повторять вслепую |
| Недостаточно истории | Непрерывные дни каждого блюда; пропуск не равен нулю |
| Закупка отклоняет склад | Exact target-date snapshot, полнота партий/нулей и сверка открытого журнала |
| Correction блокирует проводки | Freshness; исправленный остаток разрешается count anchor, source identity им не меняется |
| Recipe CSV не принимает новую версию | Legacy CSV и датированная активация — разные механизмы |
| Optimal с shortage | Это лучшее допустимое решение при ограничениях, дефицит показать менеджеру |
| Порт 3000/8000 занят | Определить прежний процесс/владельца, не убивать все Python/Node |
| Тест затронул основную БД | Проверить global API import и DATABASE_URL; нужны изолированные fixtures |
| APK не видит API | Адрес компьютера, интерфейс сервера, firewall; для debug также Metro |
| Clone без ZIP/APK/backup | Артефакты локальные/ignored; отчёт не равен наличию бинарника |
