# Predas: проверить стенд перед питчем

Из корня репозитория запустите одну команду. Она проверяет доступность сайта и API, будит спящий Render, проверяет защитные HTTP-заголовки, открытую самостоятельную регистрацию и отказ неавторизованному запросу загрузки demo-данных. Скрипт работает только как HTTP-клиент: не открывает SQLite, не читает и не меняет `DATABASE_URL`.

## Быстрая проверка

Нужен Node.js 24. Playwright в этом режиме не требуется.

```text
node scripts/check_stand.mjs --url http://localhost:3000
node scripts/check_stand.mjs --help
```

Без `--url` используется `http://localhost:3000`. Допустим только origin: HTTPS либо HTTP на localhost/loopback, без пути, query, fragment и встроенных логина/пароля. Не передавайте секреты в аргументах.

Проверки выполняются последовательно:

1. **warm-up**: `GET /api/v1/health` до настоящего HTTP 200; повторы каждые 5 секунд, общее окно по умолчанию **120 секунд**. Первый запрос к спящему Render может занимать 30–60 секунд. Время пробуждения выводится отдельно.
2. **frontend**: `GET /` должен вернуть HTML приложения с `div#root` и подключением его module-script. Требуются точные значения `X-Frame-Options: DENY` и `X-Content-Type-Options: nosniff`; отсутствующие или другие значения дают FAIL.
3. **registration**: реальный `GET /api/v1/registration` должен сообщить `enabled: true`. Закрытая регистрация означает, что новый кабинет перед питчем не открыть.
4. **unauthorized demo-data**: `POST /api/v1/demo-data` без cookie, CSRF и авторизации должен вернуть **401 или 403**. Код ответа выводится. Быстрый режим не регистрирует кабинеты и не изменяет рабочие данные; этот единственный POST предназначен для проверки отказа.

Для каждого шага печатаются результат и секунды. Успех заканчивается строкой **`STAND OK`**, код выхода — `0`. Отказ заканчивается **`STAND FAILED at <step>`**, короткой причиной и кодом `1`. Наличие отвечающего `/health` само по себе не доказывает работу worker или базы; вычисление проверяет полный режим.

Обычный Vite из текущего `scripts/start.ps1` / `scripts/start.sh` не добавляет указанные защитные заголовки на HTML. Поэтому строгая проверка такого dev-адреса честно остановится на **frontend**. Для `STAND OK` нужен корректно настроенный фронтовой прокси, например существующий Pages worker или nginx. Не подменяйте заголовки в проверяющем скрипте ради успешного результата.

Анонимный ответ 401 подтверждает отказ без сессии, но backend возвращает его **до проверки Origin**. Quick отдельно не подтверждает `ALLOWED_ORIGINS`, доступность базы или worker. Origin и реальное вычисление проверяет полный маршрут; `ORIGIN_FORBIDDEN` может проявиться при регистрации.

## Полная проверка интерфейса

**Каждый запуск `--full` создаёт один СИНТЕТИЧЕСКИЙ тестовый кабинет на выбранном стенде. Запускайте полный режим не чаще одного раза перед питчем. Самостоятельная регистрация ограничена пятью регистрациями в час с одного адреса; за прокси Render этот лимит может быть общим для разных пользователей.**

Выбирайте стенд, на котором разрешены учебные данные. Быстрые проверки выполняются первыми; при их отказе кабинет не создаётся.

```text
node scripts/check_stand.mjs --url http://localhost:3000 --lang ru --full
```

Для проверки казахского интерфейса замените `ru` на `kk`, учитывая, что это будет **новый** полный запуск и ещё один кабинет. Не повторяйте `--full` автоматически после ошибок; сначала устраните причину и используйте быстрый режим.

Нужны установленные зависимости репозитория и браузер Playwright. Скрипт предпочитает Google Chrome, при недоступности пробует комплектный Chromium:

```text
npm ci
npx playwright install chromium
```

В PowerShell при запрете `npx.ps1` используйте `npx.cmd`. Полная проверка использует viewport 1440×900 в Playwright и проходит настоящий маршрут:

**Регистрация кафе в Алматы → Загрузить демо-данные → Прогноз → Закупки → Сегодня → Закрыть день → Да, работало → Профиль.**

Финальное закрытие дня **не отправляется**. Для перехода из изменённой формы скрипт использует существующий диалог отказа от несохранённых правок. Расчёт закупки и утверждение плана не входят в эту проверку. Синтетический прогноз относится к фиксированному учебному сценарию, а не к сегодняшнему дню реального бизнеса.

Случайные email `stand-check-<random>@example.invalid` и сильный пароль существуют только в памяти. Пароль не выводится, не сохраняется и не передаётся в аргументах. При browser-ошибке создаётся **один** снимок в игнорируемой `.cache/stand-check/`: поля email/пароля и видимые данные аутентификации скрываются. Cookies, storage, профиль браузера и сессия в файлы не выгружаются; браузер закрывается через `finally`.

## Облачный адрес

После настройки и развёртывания Cloudflare Pages, Render и Supabase подставьте имя своего Pages-проекта:

```text
node scripts/check_stand.mjs --url "https://<project>.pages.dev"
node scripts/check_stand.mjs --url "https://<project>.pages.dev" --lang ru --full
```

Браузер и скрипт обращаются к одному Pages-origin; `/api/*` должен проксироваться к Render существующим `apps/web/public/_worker.js`. Порядок настройки — [DEPLOYMENT_CLOUD_RU.md](commercial/DEPLOYMENT_CLOUD_RU.md). Quick-запросы будят backend через этот же маршрут.

**Облачный стенд ещё не развёрнут: реальная сквозная проверка Cloudflare/Render/Supabase не выполнялась.** Локальная проверка Pages worker не подтверждает облачный деплой, поведение настоящего workerd или PostgreSQL pooler.

## Если проверка не прошла

| Причина | Что проверить |
| --- | --- |
| Спящий Render, warm-up timeout | Дайте сервису полное окно 120 секунд, проверьте состояние Render и повторите **quick**. Не запускайте заново full ради пробуждения. |
| `API_NOT_CONFIGURED` | В Cloudflare Pages проверьте `API_ORIGIN`: HTTPS-origin Render без пути и секретов. После исправления повторите quick. |
| `ORIGIN_FORBIDDEN` | В Render проверьте `ALLOWED_ORIGINS`: точный Pages-origin, включая схему, без пути и завершающего слэша. Не отключайте Origin/CSRF-проверки. |
| frontend: нет `DENY` / `nosniff` | Проверьте фронтовой прокси и deployment. Для обычного Vite это известное ограничение dev-запуска; проверка не объявляет такой ответ безопасным. |
| Нет HTML приложения / вместо API пришёл HTML | Проверьте адрес и маршрутизацию `/api/*` между фронтом и backend. |
| registration disabled | Уточните, разрешена ли регистрация для питча; оператор проверяет `ASBOLJAM_SELF_REGISTRATION` на backend. Не меняйте production-политику без решения владельца. |
| 429 при регистрации | Лимит пять кабинетов в час на адрес. Прекратите повторять full, дождитесь освобождения лимита; используйте quick и готовый demo-кабинет. |
| HTTP 502/503/504 или connection refused | По имени шага определите сервис: frontend/Pages, API/Render или локальный web/API. Проверьте процесс и его журнал; не публикуйте cookies, пароли и строки подключения. |
| forecast timeout | Проверьте отдельный worker и очередь. Наличие страницы или поставленного задания не означает готового прогноза. Для питча используйте заранее проверенный резерв. |

Для короткой проверки отказа используйте **заведомо свободный** локальный порт; `--timeout` задаётся в секундах и не меняет стандартное окно обычного запуска:

```text
node scripts/check_stand.mjs --url http://127.0.0.1:39999 --timeout 5
```

Ожидаемый результат этого отрицательного теста — `STAND FAILED at warm-up`, код `1`.

## За пять минут до выступления

1. Запустите quick-проверку нужного адреса.
2. Убедитесь в финальной строке **`STAND OK`**. При отказе разберите указанный шаг или переходите к резерву.
3. Откройте сайт в браузере и проверьте свой готовый кабинет.
4. Оставьте вкладку живой демонстрации открытой на начальном экране.
5. Заранее откройте локальное резервное видео и проверьте воспроизведение без сети.

Второй этап — обновление `main`, новый отдельный стенд и перезапись demo-видео — **не выполняется до явного сообщения Болата `main слит`**. Эта проверка не меняет ветку `team/bekzat-demo`, не сливает PR #2 и не создаёт автоматизацию ожидания.

Существующий `scripts/start.ps1` запущен с **новой** SQLite-базой в `.cache/stand-check-runtime-<uuid>/runtime.sqlite`: явный `DATABASE_URL` задан до миграции, seed, API и worker. Скрипт проверки не открывал БД и не менял её конфигурацию. Рабочая `data/asboljam-kz.sqlite` не открывалась; обе default-базы в checkout отсутствовали. После тестов стенд остановлен.
