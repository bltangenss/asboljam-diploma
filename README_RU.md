# AsBoljam

Рабочий учебный проект для менеджера кафе/столовой: импорт продаж → прогноз блюд на один день → ингредиенты и склад → план закупки → решение менеджера. Веб-интерфейс — на казахском языке. Все поставляемые данные **SYNTHETIC**. Сценарий: **01.01.2026**, история заканчивается **31.12.2025**.

Проверка всех исходных материалов и обнаруженные расхождения: [docs/SOURCE_REVIEW_RU.md](docs/SOURCE_REVIEW_RU.md). Файлы пользователя в Downloads не изменялись.

## Быстрый запуск в Windows

Проверенная среда разработки: Python **3.13.9**, Node.js **24.14.1**. Нужны Python, Node.js/npm и доступ к реестрам пакетов для первой установки.

В PowerShell, из корня проекта:

```powershell
.\scripts\start.ps1 -Install
```

Скрипт создаёт `.venv`, устанавливает зависимости из `requirements.lock` и `package-lock.json`, применяет миграцию, импортирует 9 CSV и запускает API, worker и web в скрытых фоновых процессах. Откройте **http://localhost:3000**.

Администратор: **admin@asboljam.local**. При первом запуске CLI напечатает случайно сгенерированный пароль один раз. Сохраните его. Можно заранее задать собственный пароль длиной от 12 символов через переменную `DEMO_PASSWORD`; он не попадёт в исходники или журналы приложения. Повторный seed сохраняет существующий пароль.

Повторный запуск и остановка:

```powershell
.\scripts\start.ps1
.\scripts\stop.ps1
```

Логи: `.cache/logs/`. Если PowerShell запрещает запуск локального скрипта, используйте ручной запуск ниже либо разрешённую вашей средой execution policy. Не запускайте второй комплект серверов на занятых портах 3000/8000.

## Linux и macOS

```bash
bash scripts/start.sh --install
# Далее:
bash scripts/start.sh
bash scripts/stop.sh
```

Синтаксис shell-скриптов проверен отдельно. Полный запуск через `start.sh` на Linux/macOS-хосте не выполнялся; подтверждённый запуск Linux-контейнеров Docker описан ниже и не заменяет эту проверку launcher.

## Ручной запуск

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
npm.cmd ci
.\.venv\Scripts\python.exe database/migrate.py
.\.venv\Scripts\python.exe scripts/seed_demo.py
```

Затем в трёх терминалах:

```powershell
.\.venv\Scripts\python.exe -m uvicorn apps.api.main:app --host 127.0.0.1 --port 8000
.\.venv\Scripts\python.exe -m apps.worker.main
npm.cmd run dev
```

В Linux/macOS путь к Python — `.venv/bin/python`, npm — `npm`. API: `http://127.0.0.1:8000/docs`. Без отдельного worker задания останутся `queued`.

Приложение по умолчанию использует `data/asboljam.sqlite`. Скрипты `start` читают локальный `.env` как пары `KEY=VALUE`, без исполнения его содержимого. При ручном запуске устанавливайте нужные переменные в окружении процесса. Образец — [.env.example](.env.example).

## Docker и PostgreSQL

Docker Desktop/Engine должен быть запущен. Скопируйте `.env.example` в `.env` и заполните `POSTGRES_PASSWORD` случайной URL-safe строкой; например, значение можно сгенерировать командой `python -c "import secrets; print(secrets.token_urlsafe(32))"`. Готового пароля в проекте нет.

```powershell
docker compose up --build -d
docker compose exec api python scripts/seed_demo.py
```

CLI напечатает отдельный пароль администратора. Откройте `http://localhost:3000`. PostgreSQL хранится в named volume `postgres_data`; на хост порт базы не публикуется. `docker compose down` останавливает сервисы с сохранением volume.

```powershell
docker compose logs --tail 100 api worker web
docker compose config --no-interpolate --quiet
```

Контейнеры API/worker/web и PostgreSQL 17.11 действительно запускались. В отдельном проекте `asboljam-verification` 18 API-тестов прошли на PostgreSQL; версии, seed counts и image ID сохранены в [artifacts/verification/postgres.json](artifacts/verification/postgres.json). Проверочный проект использовал 3010/8010; обычный запуск выше использует 3000/8000. Теги базовых образов остаются без закрепления digest; для целевой среды их следует зафиксировать отдельно. Проверенный Docker runtime не подтверждает публичное размещение, TLS или нагрузочную готовность.

Отдельный HTTP-сценарий через nginx и работающий отдельным процессом worker прошёл 77 проверок: [runtime.json](artifacts/verification/runtime.json) сохраняет результаты и границы покрытия. Dump PostgreSQL восстановлен в новую БД; совпадение количества строк таблиц, password hashes и миграции зафиксировано в [postgres-backup.json](artifacts/verification/postgres-backup.json). Сам dump содержит служебные данные и исключён из Git/ZIP. Это проверка восстановления demo-базы; целевое production-восстановление требует своей проверки.

Для HTTPS задайте `COOKIE_SECURE=true` и точные `ALLOWED_ORIGINS` своего сайта. Публичное развёртывание, сертификаты и внешние заказы не выполнялись.

## Демонстрация

1. Войти с созданной учётной записью и выбрать филиал.
2. Проверить «Сатылымдар», даты и фильтр блюда. Экспорт сохраняет весь выбранный диапазон.
3. В «Импорт» загрузить CSV по схеме из `data/raw`, посмотреть ошибки, затем подтвердить валидный импорт. Повтор существующих ключей отклоняется целиком.
4. Создать прогноз с origin `2025-12-31`; дождаться worker. Доступны seasonal naive, rolling mean и HistGradientBoosting.
5. Создать закупку по прогнозу и бюджету; проверить ингредиенты, упаковки, стоимость, дефицит и ограничения.
6. Менеджер/администратор утверждает или отклоняет план. Для дефицита требуется явное подтверждение. Выгрузить CSV и проверить аудит.

Все девять исходных CSV уже загружены seed-командой. Их повторная загрузка специально выдаёт дубликаты. Для успешной демонстрации нового импорта используйте новый естественный ключ с валидными справочными ссылками; не заменяйте исторические файлы.

Утверждение — внутреннее решение. Приложение не отправляет заказ поставщику. Рабочий горизонт — один день; даты демо не сдвигаются к сегодняшнему дню.

## Архитектура и ограничения

- Web — React/TypeScript/Vite вместо рекомендованного Next.js; расчёты полностью выполняет Python backend/worker.
- Хранилище — SQLAlchemy, SQLite для локального демо и проверенный PostgreSQL runtime для Compose. Миграция `0001` собственная, без Alembic. Операционные строки — валидированные JSON с уникальными ключами; внешние ссылки проверяются транзакционно приложением, а не отдельными SQL FK каждой CSV-схемы.
- Очередь заданий — долговечная таблица БД, отдельный worker; Celery/Redis не используются. Повтор после аварии — через 30 минут. Для длительных заданий потребуется heartbeat.
- Нет полного складского движения, смены активных версий рецептов, интеграции с кассой и автоматических заказов. Поставляемый импорт принимает только `SYNTHETIC` и поддерживаемые единицы `kg`/`L`.
- Oracle и параметры генератора не входят в API, признаки моделей и seed. Базовые модели не имеют квантилей; p10–p90 у HGB — номинальный 80% интервал.

## Офлайн-подготовка данных предприятия

[POS-адаптер](docs/POS_ADAPTER_RU.md) поддерживает явное сопоставление агрегированных дневных продаж и снимков партий. Он проверяет даты, идентификаторы, Decimal, единицы и дубли; не подключается к кассе или БД. По умолчанию dry run ничего не записывает. Только `--write` создаёт новый пакет внутри игнорируемого `.cache/enterprise-adapter`.

`REAL` сохраняется как `REAL`; импорт таких записей в текущее SYNTHETIC-приложение намеренно недоступен. Все поставляемые примеры искусственные; совместимость с конкретным предприятием не подтверждена. Персональные/oracle поля и неизвестные колонки отвергаются, но фильтр не заменяет полный аудит персональных данных. Реальные входы, mapping с чувствительными названиями и результаты нельзя включать в Git или распространяемый ZIP. Research runner отдельно отвергает REAL, mixed и отсутствующее происхождение до расчётов и записи артефактов.
