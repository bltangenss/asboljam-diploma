# AsBoljam — мобильный клиент

Отдельный клиент React Native + Expo + TypeScript в `apps/mobile`. Он обращается к тому же FastAPI, что и веб-приложение, и использует `packages/api-client/index.ts`. ML и закупочные вычисления на телефоне не дублируются.

Реализованы вход, восстановление сессии, пять вкладок, выбор разрешённого филиала, обзор, списки/детали прогнозов и закупок, складские партии, профиль, казахский/русский интерфейс и выход. Менеджер может онлайн утвердить или отклонить существующий план. Создание расчётов и импорт доступны через веб-клиент.

Данные сохраняют отметку `SYNTHETIC` и дату сценария **01.01.2026**. Время последнего HTTP-чтения показывается отдельно и не изменяет историческую дату склада.

## Установка и запуск

Нужны Node.js поддерживаемой LTS-ветки, запущенный сервер AsBoljam, созданная серверная учётная запись и загруженные демонстрационные данные. Mobile имеет собственные `package.json` и lockfile; корневой веб-пакет не изменяет.

В PowerShell из корня проекта:

```powershell
Set-Location apps/mobile
npm.cmd ci
Copy-Item .env.example .env
npm.cmd run typecheck
npm.cmd test
```

Копировать `.env.example` следует только если собственный `.env` ещё не создан. Переменная `EXPO_PUBLIC_API_URL` — публичный URL вида `http://10.0.2.2:8000/api/v1`, без токенов и паролей.

- Android Emulator использует `10.0.2.2` для обращения к компьютеру разработчика.
- Физическому устройству нужен достижимый адрес API. `localhost` на телефоне обозначает сам телефон. Для сети разработки потребуется запуск API на подходящем интерфейсе и разрешённый порт Windows Firewall; база данных наружу не открывается.
- Для внешнего API используйте HTTPS. Пример HTTP предназначен для локальной разработки.
- Native-сборки используют отдельные токены; настройки браузерных cookies сюда не переносятся.

После установки Android Studio, SDK и JDK 17/21 соберите development APK из корня репозитория:

```powershell
.\scripts\build_android_debug.ps1 -Architecture x86
```

`x86` предназначен для совместимого эмулятора. Для телефона выберите ABI устройства, например `-Architecture arm64-v8a`; успешная x86-сборка не доказывает сборку других ABI. Скрипт использует один worker, сохраняет Gradle/Expo caches в `.cache` и допускает явные `-JavaHome`, `-AndroidSdk`, `-GradleUserHome`. При первом запуске нужны сеть и свободное место для Gradle, JDK toolchain, Android SDK/NDK и зависимостей. Путь SDK должен быть доступен на запись, если недостающие компоненты будут загружаться автоматически; лицензии Android SDK должны быть приняты владельцем.

Скрипт передаёт `scripts/android-gradle.init.gradle`: только устаревший Foojay resolver заменяется на 1.0.0 для совместимости с Gradle 9. Установленные npm-пакеты и глобальные Gradle-настройки не редактируются. Причина — удалённое поле IBM_SEMERU, на которое ссылается версия 0.5.0 из RN Gradle plugin; [исправление Foojay](https://github.com/gradle/foojay-toolchains/blob/main/CHANGELOG.md). Прямой `npm run android` обходит этот init script и в закреплённом наборе зависимостей может снова получить ту же ошибку.

После успешной сборки и подключения собственного тестового устройства/эмулятора:

```powershell
adb install apps/mobile/android/app/build/outputs/apk/debug/app-debug.apk
Set-Location apps/mobile
npm.cmd start
```

Установка не перезаписывает существующее приложение автоматически: сначала проверьте его наличие и данные. Debug development client требует запущенный Metro для JavaScript приложения. Изменение native-зависимостей требует пересборки. Для локального `npm.cmd run ios` нужна macOS с Xcode. Облачная сборка, release signing, аккаунты разработчика и публикация не выполнялись.

QR-код dev-сервера, TypeScript и JavaScript-тесты не доказывают наличие APK/IPA. Фактический результат native-сборки и проверки устройства находится в [VERIFICATION_RU.md](VERIFICATION_RU.md).

## Серверный контракт и сессия

Клиент прочитан и реализован по существующему `apps/api/main.py`:

| Действие | Endpoint |
| --- | --- |
| Native-вход | `POST /api/v1/auth/token` |
| Ротация refresh | `POST /api/v1/auth/refresh` |
| Выход и отзыв refresh-семейства | `POST /api/v1/session/logout` с Bearer |
| Филиалы и блюда | `GET /api/v1/branches`, `GET /api/v1/meals` |
| Обзор | `GET /api/v1/dashboard?branch_id=...` |
| Прогнозы | `GET /api/v1/forecasts`, `GET /api/v1/forecasts/{id}` |
| Планы | `GET /api/v1/plans`, `GET /api/v1/plans/{id}` |
| Решение менеджера | `POST /api/v1/plans/{id}/approve` или `/reject` |
| Склад | `GET /api/v1/inventory?branch_id=...` |

Access token находится только в памяти. Refresh token и адрес API сохраняются через Expo SecureStore; смена адреса не отправляет старый токен другому серверу. Пароль, полные таблицы, access token и пользовательский профиль не сохраняются на диск. `AsyncStorage` и browser storage не используются. На iOS выбран доступ к ключу только после разблокировки и без переноса на другое устройство.

Сервер выдаёт access на 15 минут и ротируемый refresh; клиент объединяет параллельные обновления в один запрос. Новый refresh сохраняется до последующих API-запросов. `401` допускает одно обновление авторизации и повтор исходного запроса; `403`, `409` и сетевой сбой автоматически не повторяют бизнес-операцию. Выход очищает локальную сессию даже при сетевой ошибке, но в этом случае серверный отзыв не заявляется успешным. Ошибка SecureStore показывается, небезопасного резервного хранилища нет.

Для утверждения передаются `expected_version`, `reason`, `acknowledge_shortage` и `Idempotency-Key`. Пока полезная нагрузка не изменилась, явная повторная отправка в текущем экране использует тот же ключ. Перед действием есть подтверждение, что заказ поставщику не отправляется. После конфликта требуется обновить и повторно просмотреть план.

## Сеть, роли и данные

Нет дискового кеша таблиц и очереди офлайн-действий. При потере связи виден баннер, изменение плана недоступно. Уже отображённая в памяти информация имеет время получения и пометку возможного устаревания. Возвращение в приложение/восстановление сети обновляет чтение с сервера и не подтверждает планы автоматически.

Смена филиала очищает экран; запоздавший ответ предыдущего запроса не заменяет данные нового филиала. Сервер остаётся окончательным источником прав; подмена ID проверяется его тестами. Для складского сотрудника начальная вкладка — склад, недоступные серверные разделы показывают отказ. В базовых моделях квантили отсутствуют; p10–p90 обозначается как номинальный 80% интервал. Суммы различных физических единиц не выводятся.

## Проверки

`npm.cmd run typecheck` проверяет TypeScript приложения и общий клиент.

`npm.cmd test` компилирует и запускает Node-тесты контроллера сессии с подменённым HTTP и хранилищем:

1. Только refresh token сохраняется, native-запрос не использует browser cookies.
2. Параллельные запросы выполняют одну ротацию refresh.
3. Восстановление обновляет refresh, другой API не получает чужие credentials.
4. Повтор после `401` сохраняет версию, подтверждение дефицита и idempotency key.
5. Отказ филиала `403` и конфликт `409` не повторяются автоматически.
6. Сетевая ошибка выхода не оставляет локальную сессию.
7. Отозванный/reused refresh завершает сессию.
8. Поздний ответ refresh после очистки не восстанавливает credentials.

Эти тесты проверяют логику клиента с имитацией SecureStore. Шифрование ОС, клавиатура, accessibility, реальная сеть, Android/iOS и весь путь на телефоне требуют проверки development build. Серверная изоляция, ротация/отзыв и идемпотентность также проверяются отдельными backend-тестами.

Результаты реально выполненных команд записаны в `VERIFICATION_RU.md`.
