# AsBoljam: веб-жүйені әзірлеуге арналған негізгі промпт

Сен осы репозиторийдегі бағдарламаны іске асыратын full-stack әзірлеушісің. Төмендегі тапсырма бойынша тек кеңес немесе экран суретін емес, іске қосылатын, тексерілетін веб-жүйенің кодын жаса. Жауаптар мен интерфейстің негізгі тілі — қазақша. Код идентификаторлары — ағылшынша.

## 1. Жобаның мәні

Диплом тақырыбы: «Қоғамдық тамақтандыру кәсіпорындары үшін сұранысты болжаудың зияткерлік жүйесін және сатып алуды оңтайландыруды әзірлеу». Өнімнің жұмыс атауы — AsBoljam; атауды конфигурацияда ауыстыруға болады, ал MVP-де ұйым баптауы тек оқылады. Бұл клиентке тағам сататын интернет-дүкен де, таныстырылым лендингі де емес. Бұл асхана/кафе менеджеріне арналған ішкі жұмыс жүйесі. Негізгі тізбек: сатылымды импорттау → деректі тексеру → тағам сатылымын болжау → рецепт арқылы ингредиент қажеттілігі → жарамды қор → шектеулері бар сатып алу ұсынысы → адамның бекітуі.

Маған алдымен веб-нұсқа керек. Кейін сол backend пен API-ді қолданатын мобильді қосымша қосылады. ML және сатып алу логикасын браузерге немесе тек Next.js серверлік әрекеттеріне байлама.

## 2. Код жазудан бұрын оқылатын файлдар

Алдымен README_KK.md, AGENTS.md, docs/01_PRODUCT_REQUIREMENTS_KK.md, docs/02_ARCHITECTURE_KK.md, docs/03_DATA_RULES_KK.md, docs/04_ML_PROCUREMENT_KK.md және docs/05_TESTS_AND_ACCEPTANCE_KK.md файлдарын оқы. Содан кейін contracts/openapi.json, contracts/data_manifest.json, database/postgres_schema.sql, design/tokens.json, design/screens.json және prompts/02_DESIGN_KK.md файлдарын тексер.

scripts/prepare_demo.py мен tests/test_preparation.py — деректерді дайындауға арналған бастапқы код. data/demo.sqlite — тек деректерді тасымалдауға арналған SQLite мысалы; оны дайын өндірістік backend деп қабылдама. data/fixtures ішіндегі JSON — жазылған демо-нәтижелерден алынған интерфейс мысалдары. legacy/run_demo.py — алдыңғы біркүндік есептеу прототипі; ол дайын веб-сервис емес.

Файлға қолжетімділік болмаса, оны оқыдым деп айтпа: нақты жетіспейтін файлды ата. Деректердің бастапқы бағандарын болжап алмастырма. Өндірістік схема мен бастапқы CSV арасындағы сәйкестікті contracts/data_manifest.json бойынша жаса.

## 3. Ұсынылған технологиялық шешім

Web: Next.js App Router + TypeScript, Tailwind CSS, қолжетімді UI компоненттері, график кітапханасы. Backend: Python + FastAPI, SQLAlchemy + Alembic, PostgreSQL. Ұзақ ML/оңтайландыру жұмыстары API процесінен бөлек worker-де орындалсын; MVP-де Celery + Redis қолдануға болады, есептің түпкі мәртебесі PostgreSQL-де сақталсын. API — /api/v1.

Бұл стек — осы жинақ үшін ұсынылған жобалық шешім, университет бекіткен талап емес. Нұсқаларды іске асыру күніндегі ресми құжаттамамен тексер, үйлесімді тұрақты шығарылымдарды таңда, lockfile-ға бекіт. Бірнеше жыл бұрынғы шаблон пәрмендерін тексермей көшірме. Орнатылмаған тәуелділікті немесе жұмыс істемеген build-ті сәтті деп көрсетпе.

Монорепозиторийді apps/web, apps/api, apps/worker, packages/api-client, packages/design-tokens, infra, tests етіп ұйымдастыр. Болашақ apps/mobile ортақ API клиентін қолданады, бірақ web компоненттерін тікелей native компоненттер деп есептемейді. MVP үшін Kubernetes, микросервистер шоғыры, міндетті ақылы LLM немесе күрделі MLOps платформа қажет емес.

## 4. Деректер және демо уақыты

data/raw ішіндегі 9 CSV операциялық импортқа арналған: branches, meals, ingredients, recipes, suppliers, supplier_offers, calendar, daily_sales, inventory_lots. daily_sales.csv ішінде 26 316 жол; 3 бөлімше, 12 тағам, 2024-01-01–2025-12-31 кезеңі бар. Бағалар, жарамдылық мерзімдері және ұйым атаулары — SYNTHETIC оқу мысалы.

research_only/oracle_do_not_train.csv файлындағы latent_demand_ORACLE_ONLY ешбір өндірістік импортқа, feature pipeline-ға, модельге немесе API жауабына кірмесін. meals.base_daily_demand және branches.demand_multiplier — генератор параметрлері, болжам белгілері емес.

Бастапқы демо: historical_sales_end=2025-12-31, forecast_target=2026-01-01, inventory_snapshot=2026-01-01. Қойма кесіндісі сол күннің операциялары басталмай тұрған күйі деп белгіленеді. Даталарды бүгінгі күнге үнсіз жылжытпа. Интерфейсте «Демо: жасанды деректер» және «Сценарий күні: 01.01.2026» көрініп тұрсын. Қазіргі күнге қатысты нақты жоспар жасау үшін жаңа дерек пен қойма кесіндісі қажет екенін көрсет.

MVP болжам көкжиегі — 1 күн. 7/14/30 күн батырмаларын жұмыс істеп тұрғандай көрсетпе: олар келесі кезең ретінде ажыратылсын. Бастапқы жоспар 1-бөлімше үшін сақталған; басқа бөлімшеге фильтр қойғанда сол жоспардың сандарын қайталама.

## 5. Пайдаланушылар мен рұқсаттар

Әкімші пайдаланушыларды, ұйым және бөлімше рұқсаттарын басқарады. Менеджер өзіне берілген бөлімшелер бойынша деректерді көреді, есеп іске қосады, жоспарды бекітеді не қабылдамайды. Аналитик деректерді зерттеп, болжам/жоспар есептейді, бірақ бекітпейді. Қойма қызметкері өз бөлімшесінің қорын импорттайды және қарайды; пайдаланушы рөлдерін өзгертпейді.

Рөл мен organization_id сервердегі сессиядан анықталсын. Клиент жіберген рөлге, жасырылған батырмаға немесе branch_id-ге соқыр сенбе. Әр endpoint, файл экспорты, run_id және plan_id сұрауы ұйым/бөлімше құқығын тексерсін. Бір ұйымның дерегі екінші ұйымға өтпейтін интеграциялық тест жаз.

Демо пайдаланушыны құратын жеке CLI жаса; парольді қауіпсіз генерацияла немесе оператордан ал. Ортақ admin/admin паролін production-ға енгізбе. Құпияларды .env.example-да нақты мәнімен жазба.

## 6. Міндетті экрандар

/login — кіру. /dashboard — таңдалған бөлімше мен күнге арналған көрсеткіштер. /imports — CSV таңдау, алдын ала тексеру, қателер, транзакциялық импорт. /sales — фильтрленген сатылым мен экспорт. /forecasts — есептер тізімі, жаңа біркүндік есеп. /forecasts/[id] — нақты тарих, p10/p50/p90, модель және дерек кесіндісі. /recipes — рецепт және бір порциядағы мөлшер. /inventory — күндік партиялық қалдық, мерзімі өту ескертулері. /suppliers — ұсыныстар, қаптама, MOQ, мерзім. /procurement — жоспарлар тізімі. /procurement/[id] — қажеттілік, қор, қаптама, құн, тапшылық және бекіту. /reports — метрикалар және эксперименттер. /settings — ұйым/тіл/пайдаланушы рұқсаттары. /audit — өзгерістер журналы.

Бастапқы анықтамалықтар мен рецепттерді CSV импорт арқылы басқаруға болады. Толық қолмен CRUD және қойма қозғалысының өндірістік есебі кейінгі кезеңге жатады; іске асырылмаған әрекет үшін жалған «Сақталды» хабарламасын шығарма.

## 7. CSV импорт

Кодтама: UTF-8 немесе UTF-8 BOM; күн: YYYY-MM-DD; ондық белгі: нүкте. source ID жолдық идентификатор ретінде сақталсын. Әр файлдың міндетті/рұқсат етілген бағаны, типі, құрама кілті және сілтемесі manifest-тен алынсын. Бос мән мен нөлді ажырат. Қайталанған күн–бөлімше–тағам кілтін қосып жіберме.

Алдымен preview: жарамды жолдар, қателер, row_number, field, code, message. Тексеруден өтпеген импорт дерекқорды өзгертпейді. Commit бір транзакцияда орындалсын. Қайта жүктеу режимі бастапқыда reject_duplicates; кейін replace_scope қосылса, ауыстырылатын күн/бөлімше ауқымы алдын ала көрсетіліп, расталсын.

Файлдың көлем/жол шектеуін конфигурацияла; бастапқы ұсыныс — 20 MiB және 250 000 жол. Бұл сервер өнімділігі туралы өлшенген мәлімдеме емес. Тек CSV қабылда; ZIP, pickle, joblib және орындалатын файлдарды бұл endpoint қабылдамасын. Оригинал атауды дискілік жол ретінде пайдаланба. Экспортта мәтіндік ұяшықтардың формула-инъекциясынан қорғануын қамтамасыз ет.

## 8. Болжам модулі

Мақсат — observed units_sold; оны толық қанағаттандырылмаған сұраныс деп атама. Бастапқы модельдер: seasonal_naive_7, rolling_mean_28, HistGradientBoosting. p10/p50/p90 бөлек квантильдік модельдерден алынуы мүмкін. Оқыту тек forecast_origin-ге дейінгі деректермен жүргізіледі. Лаг/орташа тек өткеннен есептеледі; болашақ actual мәндері мен oracle пайдаланылмайды.

Қабылданатын белгілер docs/04_ML_PROCUREMENT_KK.md-де шектелген. Болашақ promo, price, open flag, event және ауа райы үшін алдын ала белгілі дерек не ашық жазылған сценарий керек. Файлда жоқ болашақ ауа райын нақты өлшем ретінде ойлап қоспа.

Барлық модель бірдей уақыттық test ауқымында бағалансын. MAE, RMSE, WAPE, bias, квантильдік қамту және тесттегі жол саны сақталсын. Нақты сатылымдардың қосындысы нөл болса, WAPE=null және түсіндірме. p10–p90 номинал орталық аралығы — 80%; оны «90% дәлдік» деме. Квантильдер монотонды және теріс емес болсын; түзету қолданылса, бастапқы crossing rate сақталсын. Модельдің оқу seed-і, feature list, дерек hash-і, runtime нұсқалары және нақты train/test шекарасы сақталсын.

Квантильсіз базалық модельде point_forecast міндетті, ал p10/p50/p90 үшеуі де null болсын. Ондай модельге жалған белгісіздік аралығын салма; сатып алуда point стратегиясы қолданылады. p50 және p90_stress тек тиісті квантильдер бар болғанда қолжетімді.

Демо fixtures арқылы экран жасауға болады, бірақ API өшсе, mock-қа үнсіз ауыспа. DEMO_REPLAY мен LIVE_COMPUTE режимдерін көрінетін түрде ажырат. Қай режимде қандай есеп шынымен орындалғанын журналда.

## 9. Ингредиент қажеттілігі және сатып алу

Бір ингредиент үшін gross_requirement = Σ(meal_forecast × net_qty_per_portion / yield_factor). yield_factor-ды бір рет қана қолдан. Өлшем бірлігі ingredients.unit арқылы беріледі; kg мен L бір көрсеткішке қосылмасын. unit_cost_kzt — базалық бірлік бағасы, қаптама бағасы емес: line_cost = packs × pack_qty × unit_cost_kzt.

Қойма кесіндісі шешім сәтіне қолжетімді болуы керек. expiry_date мақсат күнінен ерте партия есепке алынбайды; expiry_date=target_date осы демо келісімі бойынша жарамды. Кесіндінің күні сәйкес емес болса, операциялардың аралық қозғалысы жоқ кезде қорды ағымдағы деп көрсетпе.

MILP бүтін қаптама, MOQ, max_packs, бюджет, жеткізу мерзімі және әр ингредиент сыйымдылығын ескерсін. source offers.lead_time_days басым, supplier default тек анықтамалық. Бастапқы біркүндік сценарийде тек сол күні келетін ұсыныстар жарамды. Жеткізу шығыны мен салық бастапқы деректе жоқ; олар қамтылды деп айтпа.

p90 мәндерінің қосындысын таңдау — stress heuristic, бірлескен 90% қамтамасыз ету кепілдігі емес. shortage пен excess әр ингредиент үшін өз бірлігінде көрсетілсін. Шешуші мәртебесі мен шектеулерді қайта тексеру бөлек сақталсын. Тапшылық нөл болмаса, оны қызыл/сары ескерту және нақты жолмен көрсет. Нөл бюджет, қолжетімсіз жеткізуші, жарамсыз қойма және solver time limit жағдайларын жасырма.

## 10. Бекіту және қайта орындау қауіпсіздігі

Жоспар күйлері: draft → ready → approved немесе rejected; аяқталған нұсқа архивтелуі мүмкін. Есептеу жұмысының queued/running/succeeded/failed күйлері жоспар күйінен бөлек. Жоспар өзгерсе, жаңа version жасалып, ескі бекіту жарамсыз болады.

Approve сұрауы expected_version, reason және acknowledge_shortage өрістерін қамтысын. stale version → 409. Менеджер тапшылық бар жоспарда оны арнайы растауы керек. Бірдей Idempotency-Key мен бірдей сұрау сол нәтижені қайтарады; сол кілтпен басқа payload → 409. Бекіту, аудит және күйді өзгерту бір транзакцияда орындалсын. Екі пайдаланушы бір уақытта бекітсе, екі бөлек әрекет/тапсырыс пайда болмасын.

MVP жеткізушіге тапсырысты автоматты жібермейді. «Бекітілді» — тек ішкі шешім; «Жеткізушіге жіберілді» мәртебесін ойлап шығарма. Болашақ интеграция — жеке келісілген модуль.

## 11. API келісімшарты

contracts/openapi.json — қолмен дайындалған бастапқы келісімшарт. Backend-те оны нақты Pydantic үлгілерімен жүзеге асырып, шығарылған OpenAPI-мен сәйкестігін тестіле. Құжатталған endpoint бар болғаны үшін жүзеге асты деп есептеме.

Деректер тізімдеріне фильтр, limit/cursor; default limit=50, max=200. Ақша мен өлшемдік мөлшерді decimal string түрінде бер. Болжам/метрика floating-point бола алады. Жауапта data_origin, scenario_date немесе сәйкес as_of, run_id және warning өрістері болсын. Қате коды машинаға тұрақты, мәтіні аударылатын болсын. Ұзақ жұмыс POST → 202 + run_id → GET /runs/{run_id}.

## 12. Қауіпсіздік және пайдаланылу

Web сессиясы — HttpOnly, Secure, SameSite cookie; мемлекеттік құпия не жеке дерек қажет емес. Өзгертетін сұрауларға CSRF қорғанысы, Origin тексеруі, серверлік рөлдік рұқсат және rate limit керек. Өндірісте HTTPS; рұқсатсыз CORS '*'+credentials қолданба. Токенді localStorage-қа салма. Пароль хэші сенімді кітапханамен есептелсін.

Логтар пароль/токен/жүктелген файлдың толық мазмұнын жазбасын. Импорт пен модель артефактілері public қалтасында тұрмасын. Бэкап және қалпына келтіру сынағы болсын. Клиент жіберген модель файлын десериализациялама.

## 13. Дизайн

prompts/02_DESIGN_KK.md пен design файлдарын қолдан. Ашық, таза, кәсіби операциялық интерфейс жаса. Қазақша таңбалар: Ә Ғ Қ Ң Ө Ұ Ү Һ І дұрыс көрінсін. Ақша ₸, күн dd.MM.yyyy, бастапқы тіл kk-KZ. Десктоп және телефонда жұмыс істесін. Барлық экранда loading/empty/error/permission-denied және маңызды жерде stale/offline күйлері болсын.

## 14. Жұмысты кезеңмен орында

A: репозиторий, орта, DB migration, авторизация, дерек импорты. B: sales және анықтамалық экрандары. C: baseline forecast → уақыттық тест → квантильдік модель. D: қажеттілік, MILP, жоспар және бекіту. E: толық UI, экспорт, аудит және end-to-end тест. F: Docker Compose, нұсқаулық, демонстрация. Әр кезеңде нақты орындалған тексеруді templates/PROGRESS.md файлына жаз.

Алдымен файлдар мен деректерді тексеріп, қысқа іске асыру жоспарын бер де A кезеңін кодтауға кіріс. Бір жауапта бәрі бітпесе, орындалмағанын толық орындалды деп жаппа; келесі қадамды нақты файл/тест деңгейінде қалдыр.

## 15. Міндетті тапсыру нәтижесі

Толық бастапқы код; PostgreSQL migrations; дерек импорттаушы; seed/demo режимі; frontend/backend/worker; .env.example; тәуелділік lockfile-дары; Docker Compose; автоматты unit/integration/API/E2E тесттер; Windows және Linux/macOS іске қосу нұсқаулығы; screenshots тек шын іске қосылған интерфейстен; known limitations; есептердің метадерегі.

Кіру → CSV preview → commit → sales → forecast → procurement → manager approval → export сценарийі басынан аяғына дейін орындалмайынша «дайын» деп айтпа. Тест, build, migration орындалған пәрменін және нәтижесін көрсет. Ешбір зерттеу метрикасын, нақты үнемді, пайдаланушы пікірін немесе диплом қорытындысын ойдан шығарма. AI қолданылуын templates/AI_USAGE_LOG_KK.md-ге тіркеуге көмектес; студенттің өз талдауы мен верификациясын алмастырма.
