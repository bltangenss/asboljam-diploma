# AsBoljam — условия коммерческого запуска

Состояние: 29.09.2026. Цель — подготовить продукт к выходу на рынок. Она остаётся
активной: локально работающий SYNTHETIC workflow и зелёные тесты сами по себе не
доказывают готовность принимать данные и деньги реального клиента.

Ниже перечислены условия из этапов `01`–`05` коммерческого плана. Отсутствие бизнеса
останавливает измерение пилота, но не разработку оставшихся технических функций.

| Условие | Текущее доказательство / пробел | Следующее действие |
|---|---|---|
| Договор источника и границы одного филиала | DATA_CONTRACT и DISCOVERY_CHECKLIST подготовлены; согласованного источника предприятия нет | Сохранить schema fixtures; владелец бизнеса позже подтверждает единицы, период, timezone, рецептуры и права использования |
| Tenant как самостоятельная сущность | Scope через organization_id, роли и branch_ids проверен; отдельной модели организации со status/timezone/origin policy и операторского bootstrap ещё нет | Явная миграция, безопасное создание организации и первого администратора, проверка старой БД и пустого tenant на SQLite/PostgreSQL |
| Управление доступом и паролями | API и worker isolation; смена своего пароля и операторский reset с отзывом сессий/задач проверены на SQLite/PostgreSQL; web KK/RU проверен | Создание tenant и первого доступа; email verification/reset и принудительная смена временного пароля — отдельные незавершённые функции |
| Вход клиентских данных | Offline mapping/dry-run работает, REAL сохраняет происхождение; API намеренно SYNTHETIC-only | Реализовать отдельную tenant origin policy и versioned import provenance, без переименования REAL в SYNTHETIC; тестировать искусственные fixtures, отмеченные именно как тестовые |
| Повторяемый импорт и исправления | Preview/commit транзакционны, дубликаты отклоняются; есть scope tests | Идемпотентный повтор, происхождение/профиль загрузки, безопасная корректировка с reconciliation и аудитом без переписывания прежних решений |
| Складские движения | Есть точный dated snapshot, партии, expiry и расчёт потребности | Явный ledger приходов/расходов/списаний/корректировок с миграцией, версиями рецепта и проверкой сверки со snapshot |
| Прогноз и закупка на данных клиента | Однодневные observed-sales модели и MILP проверены на synthetic; фиксированные даты демо сохранены | Tenant-specific origin/date policy, видимый период и достаточность данных; согласованный горизонт и lead time, затем измерение качества на реальном прошлом периоде без утечки будущего |
| Надёжность длительных задач | 30-минутная аренда; старый worker не публикует повторный результат; отмена по отзыву доступа проверена | Heartbeat, контролируемое завершение процесса, проверка восстановления очереди и понятные ошибки в UI |
| Эксплуатация и наблюдаемость | Конфигурационные guards, локальные backup/restore и DB tests есть; нет целевого HTTPS развёртывания | Readiness/метрики/корреляция, редактирование секретов в логах, проверенный deployment/rollback, восстановление backup на целевой среде |
| Тарифный контур | Реального платежного подключения и API-лимитов тарифа нет | Manual pilot/invoice status, согласованные ограничения филиалов/пользователей/retention без блокировки audit/export; цены и платежи определяет владелец |
| Онбординг и поддержка | Частичный security runbook и восстановление доступа готовы | Сквозной operator onboarding, обучение, incident/escalation, export/offboarding и удаление tenant с учётом backups |
| Приёмка клиента и эффект | Полный browser путь проверен на SYNTHETIC, но нет бизнес-пилота или измеренной экономии | Согласованный pilot charter и baseline, shadow mode, реальные циклы, feedback и решение владельца; недостаточные данные прямо обозначать |
| Release package | История Git и отчёты проверяемы; старый ZIP/APK не содержит все текущие server/web изменения | После прохождения согласованных gates создать архив именно из чистого release commit, проверить содержимое, SHA256, инструкции, known limitations; mobile store release не входит в первый web-пилот |

Для заявления о выполнении каждого условия нужны код/миграция, релевантные проверки
и фактический результат в [PROGRESS](../../templates/PROGRESS.md). Deployment, account
access, юридические/платёжные решения и действия владельца фиксируются отдельно; их
нельзя подменять существованием конфигурационного файла или заранее придуманными цифрами.

Ближайший участок разработки: модель tenant и безопасный bootstrap организации,
затем отдельная граница клиентских данных и stock ledger. Незавершённые условия выше
сохраняют полный объём цели; текущая смена пароля — один завершённый участок, а не
переопределение коммерческой готовности.
