# План приготовления и закупка

Состояние: 14.10.2026. Это расширение существующего web/API. Фактические проверки и границы внедрения — в верхней записи `templates/PROGRESS.md`.

## Сценарий управляющего

1. Откройте «План дня» и рассчитайте или выберите прогноз.
2. В таблице сравните прогноз с колонкой «Приготовить». Введите целое число для каждого блюда; если блюдо готовить не нужно, укажите **0**. Пустое поле не означает ноль.
3. При необходимости нажмите «Заполнить прогнозом с округлением вверх». Это явная подсказка: она округляет каждую строку вверх до целого, после чего объёмы можно изменить.
4. Укажите название варианта и причину выбора порций. Нажмите «Сохранить новый вариант».
5. Проверьте остатки на дату прогноза и перейдите к закупке. Выбранный вариант переносится вместе с прогнозом и филиалом, в том числе после подтверждённого импорта остатков.
6. В закупке проверьте основание потребности, бюджет, упаковки, ограничения и дефицит. Утвердите или отклоните закупку отдельным действием с причиной.

Сохранённый вариант можно взять за основу нового. Прежний документ не переписывается. Новое сохранение не меняет и не отменяет ранее рассчитанную или утверждённую закупку. Общего «активного варианта» на день нет: основание выбирается явно для каждого расчёта.

## Что сохраняется

Отдельный документ содержит филиал, исходный прогноз, его целевую дату, имя варианта, причину, автора, время и полное множество блюд с целыми порциями. Рядом сохраняется исходный точечный прогноз для сравнения. Сам прогноз, квантильные интервалы и модель не изменяются; ручные решения не попадают в обучающую выборку.

Сохраняется происхождение и контекст данных. SYNTHETIC сохраняет исходные учебные даты, REAL/TEST остаётся искусственным тестом контракта. Новая версия не добавляет планирование на произвольный будущий день: дата определяется исходным прогнозом и существующими правилами бизнес-дня.

Новый вариант доступен только при подтверждённой свежести исходного прогноза. После изменения его входных данных старый документ остаётся читаемым, но для новой закупки требуется актуальный прогноз и новый вариант. Другой сохранённый вариант сам по себе не делает прежние результаты устаревшими.

## Правила расчёта

- В режиме «По прогнозу» сохраняются существующие point, p50 и p90 stress.
- При выборе плана приготовления используются именно его целые порции. p50/p90 к ним не применяются; API отклоняет такую комбинацию.
- Рецептуры, yield, точные остатки на дату, срок годности, упаковки, MOQ, максимальные количества, бюджет и вместимость проверяются прежним механизмом. Yield применяется один раз.
- Все блюда исходного прогноза должны присутствовать ровно по одному разу. Дубликаты, лишние или пропущенные ID не принимаются. Число порций — целое от 0 до 1 000 000 000; строки, дроби и логические значения API не принимает.
- Вариант, где все порции равны нулю, допустим. Даже для него остаются обязательными существующие проверки полноты рецептур и точного среза запасов. Отсутствующие сведения не заменяются нулями.
- При расчёте закупки фиксируются выбранный вариант и фактически использованные рецептуры/остатки. Выгрузка новой закупки содержит сведения о ручном основании и строки порций, включая нулевые.
- Формат старых закупок без ручного основания не дополняется пустыми колонками. Их утверждённые выгрузки остаются прежними.

## Безопасность и границы

Создавать варианты могут manager/admin, читать — разрешённые пользователи организации и филиала, включая склад. Все ограничения действуют на API. Web использует прежнюю сессию, Origin и CSRF. Сохранение требует Idempotency-Key; повтор подтверждает тот же документ, а не создаёт второй. При неизвестном исходе поля блокируются до безопасного повтора. Проверка действующих прав выполняется и при повторном запросе.

Worker повторно проверяет принадлежность варианта, неизменность исходного прогноза, контекст, свежесть, право автора и точное совпадение сохранённого основания. Исходный forecast snapshot не подменяется ручными значениями. Ручной набор для расчёта создаётся отдельно внутри вычисления. В публичном документе не раскрывается служебная ссылка на разрешение источника REAL.

Сохранение плана **не подтверждает фактическое приготовление**, не проводит расход склада, не утверждает закупку и не отправляет заказ поставщику. Фактические порции и движение ингредиентов регистрируются отдельным существующим складским документом. Отдельного согласования производственного задания, кухонных исполнителей, статусов выполнения, печати задания и автоматического учёта план/факт пока нет.

## Для разработчика

- `apps/api/production.py`: запросы, неизменяемые документы, receipt, проверка основания.
- Migration `0009`: только две новые пустые таблицы `production_plans` и `production_plan_receipts`; старые прогнозы и закупки не преобразуются в производственные планы.
- `POST /api/v1/production-plans`: `branch_id`, `forecast_id`, `name`, `reason`, `portions: [{meal_id, portions}]`; заголовок `Idempotency-Key`.
- `GET /api/v1/production-plans?branch_id=...&forecast_id=...`: пагинация `limit/cursor`; `GET /api/v1/production-plans/{id}` — документ с текущей свежестью.
- `POST /api/v1/procurement`: необязательный `production_plan_id` в паре с точным `forecast_id`, `branch_id`, `strategy: point`.
- `ProductionPlanning.tsx`: редактор, история вариантов, подтверждение сохранения и основание закупки. `Planning`, `StockLedger`, `Imports` переносят `production_plan_id` без неявной подмены.
- Девять импортируемых CSV-схем сохранены. План приготовления не является десятым импортным файлом.

Перед обновлением рабочей базы сделайте проверенную копию. На новом коде выполните миграцию и перезапустите API/worker. Успех локальных тестов не подтверждает production-развёртывание или приёмку реальным предприятием.
