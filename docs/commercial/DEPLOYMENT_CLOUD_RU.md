# Predas в облаке: Supabase + Render + Cloudflare Pages

Схема:

```text
браузер ──► Cloudflare Pages (https://<проект>.pages.dev)
             ├─ статический клиент из dist/web
             └─ /api/* ──► _worker.js ──► Render (https://predas-api.onrender.com)
                                              ├─ API (uvicorn, порт $PORT)
                                              └─ воркер очереди (в том же контейнере)
                                                   │
                                                   ▼
                                           Supabase PostgreSQL (session pooler, 5432)
```

Почему так:

- **Один адрес для пользователя.** Клиент и API для браузера живут на одном адресе. Cookie сессии (`HttpOnly`, `SameSite=Lax`, `Path=/api`), проверка `Origin` и CSRF работают так же, как за nginx. CORS и сторонние cookie не нужны.
- **Воркер в том же контейнере.** На бесплатном плане Render нет фоновых воркеров. Поэтому `infra/render_start.sh` запускает воркер в цикле перезапуска рядом с API, а Render проверяет только API (`/api/v1/health`).
- **Схема базы создаётся при старте.** На свежей базе Supabase API сам применяет миграции `0001…0012`, под защитой `pg_advisory_xact_lock`.

Файлы: `render.yaml`, `infra/render_start.sh`, `infra/Dockerfile.api`, `apps/web/public/_worker.js`. Их проверяют `tests/test_cloud_config.py` и `tests/pages_worker_check.mjs`.

## Что делает владелец (вход в аккаунты, пароли, оплата)

Порядок важен: сначала база, потом API, потом сайт.

### 1. Supabase — база

1. Войдите на supabase.com и создайте проект. Регион — **Central EU (Frankfurt)**, рядом с Render Frankfurt. Пароль базы придумайте сами и сохраните в менеджере паролей.
2. Нажмите **Connect** и выберите **Session pooler**. Скопируйте строку вида
   `postgresql://postgres.<ref>:[YOUR-PASSWORD]@aws-0-eu-central-1.pooler.supabase.com:5432/postgres`.
   - Подставьте пароль. Если в нём есть `@ : / ? #`, их нужно закодировать.
   - Допишите в конец `?sslmode=require`.
   - Используйте именно session pooler на порту 5432:
     - прямое подключение `db.<ref>.supabase.co` работает только по IPv6, а Render его не поддерживает;
     - transaction pooler на порту 6543 ломает подготовленные запросы psycopg.
3. Таблицы создавать не нужно — их создаст API при первом запуске.

### 2. Render — API и воркер

1. Войдите на render.com через GitHub и дайте Render доступ к приватному репозиторию `bltangenss/asboljam-diploma`.
2. Выберите **New → Blueprint**, укажите репозиторий и ветку `main`. Render прочитает `render.yaml` и создаст сервис `predas-api` (Docker, план Free, Frankfurt).
3. Render попросит значения переменных с `sync: false`:
   - `DATABASE_URL` — строка из шага 1.2;
   - `ALLOWED_ORIGINS` — будущий адрес сайта, например `https://predas.pages.dev`. Без слэша на конце. Если имя проекта в Cloudflare будет другим, поменяйте это значение потом.
4. Дождитесь сборки и откройте `https://<сервис>.onrender.com/api/v1/health`. Ответ должен быть `{"status":"ok"}`.

### 3. Cloudflare Pages — сайт

1. Войдите на dash.cloudflare.com, откройте **Workers & Pages → Create → Pages → Connect to Git** и выберите тот же репозиторий.
2. Настройки сборки:
   - Production branch: `main`;
   - Build command: `npm run build`;
   - Build output directory: `dist/web`;
   - переменная `NODE_VERSION` = `22`.
3. В **Settings → Variables and Secrets** добавьте `API_ORIGIN` = `https://<сервис>.onrender.com`. Только адрес, без пути и слэша.
4. После сборки откройте `https://<проект>.pages.dev`. Если адрес не совпал с `ALLOWED_ORIGINS` в Render, исправьте переменную в Render и дождитесь перезапуска.

Альтернатива без подключения Git: выполните `npx wrangler login` (вход делает владелец в браузере), затем `npm run build` и `npx wrangler pages deploy dist/web --project-name predas`. Переменную `API_ORIGIN` всё равно нужно задать в настройках проекта.

### 4. Проверка после деплоя

1. Откройте сайт → «Регистрация». Создайте тестовое заведение, выберите город и согласитесь на тестовый режим.
2. Нажмите «Загрузить демо-данные», затем «Прогноз» → рассчитайте прогноз. Расчёт выполняет воркер, это занимает около минуты.
3. Откройте «Закупки», «Закрыть день», «Профиль».
4. Утвердите план закупки и найдите запись в «Журнал действий». Утверждение не отправляет заказ поставщику.

## Важные ограничения

- **Засыпание.** Бесплатный Render засыпает после 15 минут без запросов. Первый запрос будит сервис 30–60 секунд, так что за пару минут до питча откройте сайт. Полный расчёт в это время не идёт: воркер спит вместе с API.
- **Память.** Локальный замер на Windows (20.10.2026): пик API около 230 МБ, воркера около 170 МБ при прогнозе с 20 факторами по демо-данным — вместе около 400 МБ при лимите 512 МБ. Если Render перезапускает сервис с «Out of memory», нужен план с большей памятью или отдельный воркер (`type: worker`). Это платные варианты, решение за владельцем.
- **Нет демо-входа.** В production демо-логин не создаётся: `DEMO_PASSWORD` запрещён. Каждый сам регистрирует тестовый кабинет, данные в нём помечаются SYNTHETIC.
- **Открытая регистрация.** `ASBOLJAM_SELF_REGISTRATION=on` открывает регистрацию для всех, кто знает адрес. Ограничение — 5 регистраций в час с одного адреса. После питча её можно закрыть значением `off` в Render.
- **Лимит регистраций общий.** API видит адрес прокси Render, а не браузера, поэтому лимит регистраций «5 в час» считается общим для всех. Вход ограничивается по связке «почта + адрес».
- **Бэкапы.** Бэкапы Supabase на бесплатном плане ограничены. Реальные данные предприятий в эту схему не загружаются без отдельного решения оператора.

## Что проверено, а что нет

- **Проверено локально (20.10.2026, Windows, SQLite):**
  - `sh infra/render_start.sh` с `PORT=8123` запускает API и воркер;
  - эмулятор Pages с этим же `_worker.js` отдаёт клиент и проксирует `/api`;
  - регистрация ставит `HttpOnly` cookie с `Path=/api`;
  - запрос без CSRF отклоняется — 403 `CSRF_INVALID`, без Origin — 403 `ORIGIN_FORBIDDEN`;
  - демо-данные загружаются за 4,9 с, прогноз `hist_gradient_boosting_factors` считается воркером за 26 с.
- **Не проверено:**
  - реальные Render, Cloudflare и Supabase;
  - PostgreSQL через pooler;
  - сборка Docker-образа (Docker Desktop не был запущен);
  - поведение настоящего workerd;
  - память на Linux.

Деплой считается выполненным только после проверки из раздела 4 на настоящих адресах.
