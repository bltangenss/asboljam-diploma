# AsBoljam — повторяемый импорт и исправление данных

Эта инструкция описывает текущие API импорта и происхождения расчётов. Все примеры
учебные, с `data_origin=SYNTHETIC`. Организация должна быть активной с политикой
`synthetic_only`. `unconfigured` не разрешает операционные данные. Для web-импорта REAL
оператор отдельно регистрирует источник пустой организации; политика становится
`real_only`. Назначение TEST/PILOT, один филиал, источник и требования дат описаны в
[REAL_DATA_OPERATIONS_RU.md](REAL_DATA_OPERATIONS_RU.md). Подключения к кассе и проверки
подлинности разрешения предприятия нет. Нельзя перемаркировать реальные строки как `SYNTHETIC`.

## 1. Обновление существующей базы

Работать из корня проекта. Выбрать нужную БД через явно заданный `DATABASE_URL`
в защищённой среде процесса; команды Python не загружают `.env` автоматически.
Не помещать URL с паролем в команду, документацию, лог или Git. Конфигурация проверяется
до подключения к БД, включая ограничения `production`:

```text
python -m apps.api.config
```

Перед обновлением остановить запись приложением и worker, создать backup и проверить
его восстановление. Для SQLite заменить `PATH_TO_EXISTING.sqlite` реальным выбранным
путём. Оба пути назначения должны быть новыми:

```text
python scripts/backup_db.py backup --database PATH_TO_EXISTING.sqlite --output backups/pre_0004.sqlite
python scripts/backup_db.py restore --backup backups/pre_0004.sqlite --destination backups/restore_check_pre_0004.sqlite
python database/migrate.py
```

Для PostgreSQL нужны `pg_dump` и проверка `pg_restore` в отдельную новую БД; SQLite
утилита для этого не подходит. Восстановление проверяется до переключения приложения.
Резервную копию не восстанавливать поверх действующей базы. Не запускать demo seed
или launcher с seed для обновления пользовательской организации.

Миграции выполняются последовательно: `0001` — исходные таблицы, `0002` — организации,
`0003` — `import_evidence`, `record_revisions`, `import_receipts`. Новые таблицы хранят
доказательства получения CSV, версии изменённых строк и ответы повторных запросов.
Миграция `0003` сохраняет прежние операционные строки и импорты; вымышленные источники,
хеши или ревизии старым данным не добавляются. Повторный запуск не повторяет импорт.
`0004` создаёт регистрацию `organization_sources` и расширяет политику организации,
но не активирует REAL и не меняет происхождение прежних записей.
Неизвестная либо неполная история миграций отклоняется; version markers вручную
не удалять. Создание пустой организации описано в [инструкции tenant](TENANT_OPERATIONS_RU.md).

## 2. Файлы и порядок загрузки

Сохранены девять схем. Один запрос preview принимает один тип CSV. Точные заголовки
выдаёт `GET /api/v1/imports/template/{kind}` с учётом роли пользователя.

| `kind` | Назначение | Естественный ключ строки |
|---|---|---|
| `branches` | Филиалы | `branch_id` |
| `meals` | Блюда | `meal_id` |
| `ingredients` | Ингредиенты, единицы и выход | `ingredient_id` |
| `recipes` | Состав блюд | `meal_id`, `ingredient_id`, `recipe_version` |
| `suppliers` | Поставщики | `supplier_id` |
| `supplier_offers` | Упаковки, цены и ограничения предложений | `supplier_id`, `ingredient_id` |
| `calendar` | Календарные признаки филиала | `date`, `branch_id` |
| `daily_sales` | Продажи блюд по дням | `date`, `branch_id`, `meal_id` |
| `inventory_lots` | Партии запасов на конкретную дату | `branch_id`, `ingredient_id`, `lot_id`, `snapshot_date` |

Сначала загрузить справочники, затем зависимые рецептуры/предложения и операционные
файлы. Идентификаторы остаются строками: `001` и `1` — разные ID. Денежные и физические
величины хранятся десятичными строками; `kg` и `L` не взаимозаменяемы. Повторы ключа
внутри одного файла запрещены, даже если значения совпадают. Ссылки на справочники,
единицы измерения и права филиала проверяются сервером.

Текущий учебный сценарий использует историю до `2025-12-31` и прогноз/срез запасов
на `2026-01-01`. Не переносить эти даты на сегодняшний день ради демонстрации.
Дополнительные исследовательские/генераторные поля не являются входами прогноза.

REAL сохраняет девять строгих схем: каждая строка должна иметь `data_origin=REAL`,
а поля филиала — зарегистрированный ID. `source_id` и `mapping_version` preview должны
совпасть с регистрацией, в web они подставляются автоматически. Календарное
`synthetic_event` равно `0`; доступность/stockout не выводятся из продаж. Продажи
текущего бизнес-дня и будущие snapshots отклоняются. Native REAL-операции заблокированы
с явным `403`; используйте web. Экспорты REAL с дополнительными колонками источника
являются отчётами, а не входными шаблонами.

| Роль | Создание preview и commit |
|---|---|
| `admin` | Девять схем в рамках доступных данных организации |
| `manager` | `daily_sales`, `calendar`, `inventory_lots` своих филиалов |
| `warehouse` | `inventory_lots` своих филиалов |
| `analyst` | Чтение; preview и commit запрещены |

Импорт нового филиала администратором даёт этому администратору доступ к созданному
филиалу. Повторная загрузка уже существующего чужого филиала не расширяет доступ.

## 3. Preview: сначала проверить, затем сохранить

`POST /api/v1/imports/preview` создаёт сохранённый результат проверки и возвращает
его `id`. На этом шаге операционные строки не изменяются. В web используется текущая
HttpOnly-сессия; для POST обязательны разрешённый `Origin` и `X-CSRF-Token`, полученный
при входе. В примерах ниже показано тело запроса, без паролей или токенов.

Пример предполагает, что учебные филиал `1` и блюдо `1` уже существуют:

```json
{
  "kind": "daily_sales",
  "mode": "append",
  "csv_text": "date,branch_id,meal_id,units_sold,available_portions,stockout_flag,is_open,promo,price_kzt,data_origin\n2025-12-31,1,1,20,30,0,1,0,1500.00,SYNTHETIC\n",
  "source": {
    "source_id": "training-fastfood-manual",
    "mapping_version": "canonical-v1"
  }
}
```

При отсутствии `source` применяются `source_id=manual_csv` и
`mapping_version=canonical-v1`. Эти поля — заявленные обозначения источника и
преобразования, а не запуск адаптера или подтверждение подключения кассы.

Проверять в ответе:

- `valid`, `errors` и `can_commit`: отсутствие ошибок, сообщения проверки и
  возможность commit именно текущим пользователем. Preview не резервирует данные;
  при commit проверки выполняются снова.
- `counts.new`, `unchanged`, `updated`, `conflicting`: классификация успешно
  разобранных строк относительно текущего состояния БД. При ошибках файла это
  диагностические числа, а не обещание частичного сохранения.
- `counts.rows_seen`, `rows_checked`, `parsed`: встреченные CSV-записи, записи,
  прошедшие попытку проверки парсером, и успешно разобранные строки. Заголовок
  в эти числа не входит; предел строк может дать `rows_seen > rows_checked`.
- `validation_complete`, `validation_rows_checked`, `validation_stop_reason`:
  отдельный результат проверки ссылок, доступа и существующих ключей после парсера.
  При ошибках разбора этот этап не запускается (`parser_errors`); при достижении
  предела ошибок непроверенный остаток отмечается явно.
- `scan_complete`, `stop_reason`, `errors_truncated`: завершились ли обе стадии,
  почему проверка остановилась и был ли обрезан список ошибок. `scan_complete=true`
  не означает отсутствие ошибок и допустимость commit: для этого нужны `valid`
  и `can_commit`. Даже полностью прочитанный файл может быть проверен не полностью.
- `branch_ids`, `period`: филиалы и диапазон `date`/`snapshot_date` успешно
  разобранных строк. У справочника без дат период пустой.
- `preview` и `changes`: до десяти строк и пар `before`/`after` с операцией
  `insert`, `unchanged`, `update` или `conflict`. Поле `preview_limit=10`
  обозначает предел показа, а не число проверенных строк.

По умолчанию лимиты парсера — 20 MiB полученного UTF-8 текста и 250 000 записей;
оператор может задать `IMPORT_MAX_BYTES` и `IMPORT_MAX_ROWS`. Список ошибок ограничен
500 элементами. При ранней остановке недочитанный остаток не считается проверенным.
Даже одна ошибка блокирует весь commit: допустимый префикс отдельно не записывается.
Сохранённая история preview при этом остаётся для разбора ошибки.

## 4. Какие хеши и сведения об источнике сохраняются

| Поле | Что оно означает |
|---|---|
| `received_text_sha256` | SHA-256 UTF-8 представления строки `csv_text`, полученной API. Учитывает BOM и переводы строк в этой строке. Это не хеш байтов исходного файла до декодирования в браузере/адаптере. |
| `canonical_rows_sha256` | SHA-256 отсортированного набора естественных ключей и хешей разобранных строк. Порядок строк и эквивалентное написание десятичных величин не меняют результат. При частичном разборе охватывает только разобранные строки. |
| `source.declared_original_sha256` | Необязательные 64 hex-символа, заявленные отправителем для оригинала. API не получает оригинальные байты для проверки этого заявления. |
| `source.original_hash_verified` | Всегда `false` в текущем API; клиент не может установить `true`. |
| `source.hash_version` | Текущая канонизация `canonical-v1`. Нормализация используется для сравнения, не переписывает уже сохранённое представление величин. |
| `source.timezone`, `currency` | Снимок метаданных организации при preview. Неизвестная timezone остаётся `null`; валюта берётся из организации. |
| `source.provenance` | `received_csv_text` у нового preview; не подтверждает подлинность экспортировавшей системы. |
| `source.data_origin`, `usage_mode`, `source_contract` | Для REAL фиксируют происхождение, TEST/PILOT и зарегистрированный источник версии 1; сервер повторно проверяет контекст перед commit. Операторская ссылка на разрешение не является проверенным документом. |

Хеши позволяют сравнивать содержимое, но не являются цифровой подписью, проверкой
автора файла или доказательством реальности продаж. Идентификатор организации,
автор preview, время создания/commit и причина коррекции сохраняются отдельно от
заявленных метаданных источника.

## 5. Commit и безопасный повтор запроса

После проверки ответа отправить запрос с `id`, реально возвращённым preview:

```http
POST /api/v1/imports/BATCH_ID_FROM_PREVIEW/commit
Idempotency-Key: training-sales-20251231-v1
```

Заголовок необязателен: без него сервер использует `batch:<id>`. Для интеграции
рекомендуется явно сохранять стабильный ключ на одну операцию и повторять тот же
ключ при сетевом сбое. Разрешены 1–128 символов `A-Z`, `a-z`, `0-9`, `_`, `.`, `:`, `-`.
Область ключа — организация и автор операции. Ключи импорта отделены от ключей
утверждения закупочного плана.

Успех возвращает `status=committed`, `inserted_rows`, `updated_rows`, `unchanged_rows`.
Повтор commit той же партии с тем же ключом возвращает сохранённый ответ, без новых
операционных строк, ревизий или audit-событий. Использование ключа для другой партии
даёт `409 IDEMPOTENCY_CONFLICT`. Повтор уже committed-партии с новым ключом тоже
использует прежний результат; может появиться отдельная квитанция ключа, но данные
и события commit повторно не записываются.

Повторная загрузка того же файла создаёт новый preview. При совпадающих ключах и
значениях строки имеют `unchanged`; commit новой партии не дублирует записи или
ревизии, но сохраняет собственную историю партии и событие импорта. Если между
preview и commit данные изменились, фактические счётчики commit могут отличаться
от preview. Окончательным результатом операции служит квитанция commit.

`409 IMPORT_CONCURRENT_RETRY` означает повторить commit той же партии с тем же
ключом. `DUPLICATE_CONFLICT` требует нового preview и решения о коррекции.
Ошибки валидации дают `422`; частичная запись операционных данных не выполняется.
Commit разрешён только исходному автору партии при сохранённых текущих правах.

## 6. Исправление сохранённых значений

`mode=append` добавляет новые ключи и принимает неизменившиеся существующие строки.
Другие значения для существующего ключа дают конфликт. Скрытого перезаписывания нет.

`mode=correction` поддержан только для `daily_sales`, `calendar`, `inventory_lots`.
Все ключи должны уже существовать. Нужна причина `reason` длиной 3–1000 символов
после обрезки пробелов. Это изменение значений строки с прежним ключом: удаления,
переименования ключа и автоматической отмены загрузки нет. Справочники этим режимом
не исправляются. Если ошибочен сам ключ, не маскировать это добавлением ещё одной
строки: требуется отдельно спроектированная операция исправления ключей.

Пример изменения учебных продаж с 20 до 22 порций по уже сохранённому ключу:

```json
{
  "kind": "daily_sales",
  "mode": "correction",
  "reason": "Исправление количества в учебном исходнике",
  "corrects_batch_id": "BATCH_ID_FROM_COMMITTED_IMPORT",
  "csv_text": "date,branch_id,meal_id,units_sold,available_portions,stockout_flag,is_open,promo,price_kzt,data_origin\n2025-12-31,1,1,22,30,0,1,0,1500.00,SYNTHETIC\n",
  "source": {
    "source_id": "training-fastfood-manual",
    "mapping_version": "canonical-v1"
  }
}
```

`corrects_batch_id` необязателен. Если задан, он должен указывать на доступную
committed-партию того же типа, а все ключи коррекции должны входить в эту партию.
Причина остаётся обязательной независимо от наличия ссылки. Поля `reason` и
`corrects_batch_id` не принимаются как коррекция в режиме `append`.

Перед commit сравнить `before` и `after`; для каждой действительно изменённой строки
сохраняются новая последовательная ревизия, значения до/после, их хеши, ID партии,
автор, время и причина. Операционные изменения, квитанция и audit завершаются одной
транзакцией. Неизменившаяся строка не получает искусственную новую ревизию.

Preview коррекции фиксирует ожидаемые хеш и номер ревизии. Если до commit другая
операция изменила строку, сервер возвращает `409 STALE_IMPORT`; нужно заново сделать
preview и проверить новые `before`/`after`. Даже последовательность A → B → A
не делает старый preview допустимым: номер ревизии уже изменился. Проверка распространяется
и на строки партии, которые в момент preview были `unchanged`.

Для исправления ошибочной коррекции загрузить новую коррекцию с нужными прежними
значениями и объяснением причины. Можно связать её с ошибочной через `corrects_batch_id`.
Это компенсирующее изменение: исходные партии, ревизии и audit остаются в истории.

## 7. История, доступ и старые данные

`GET /api/v1/imports?limit=50&cursor=0` возвращает доступную историю; `limit` от 1 до 200.
Следующую страницу запрашивать с возвращённым `next_cursor`, если он не `null`.
`GET /api/v1/imports/{id}` показывает детали, ограниченный preview и квитанцию.

Незавершённые previews доступны автору и администратору в пределах разрешённых
филиалов. Для собственного preview новых филиалов у администратора есть исключение,
необходимое для их создания. Committed-партии доступны другим пользователям той же
организации в рамках текущей роли и филиалов: admin/manager/analyst читают девять
типов, warehouse — `inventory_lots`, `ingredients`, `branches`. Право чтения источника
не даёт права commit чужой партии.

Если партия охватывает несколько филиалов, читатель должен иметь доступ ко всем;
сервер не выдаёт частичную историю со скрытым хвостом. Чужая организация, недоступная
партия или попытка commit чужой партии дают `404`. После отзыва роли/филиала прежняя
сессия отзывается, а новый вход использует текущие ограничения. Ошибочный preview
для чужого филиала не раскрывает сохранённые значения в `before`.

У импортов до `0003` источник отмечен `legacy_unattributed`, хеши и время commit
без сохранённых доказательств остаются `null`. Старый preview нельзя подтвердить:
`409 IMPORT_PREVIEW_REQUIRED`, нужен новый preview исходного CSV. Уже существующие
операционные строки при этом сохраняются. Отсутствие источника не подменяется
фиктивным импортом.

## 8. Как импорт влияет на прогноз и закупку

Новые задания сохраняют снимок входных данных при постановке в очередь. Worker
публикует результат этого снимка, даже если во время расчёта была разрешённая
коррекция. Источник включает хеши строк, их ревизии и связь с партиями, если она есть.

Прогноз отслеживает продажи выбранного филиала до даты начала прогноза включительно
и справочник блюд. Закупка наследует этот источник прогноза и дополнительно отслеживает
ингредиенты, рецептуры, поставщиков, предложения и партии запасов выбранного филиала
на точную целевую дату. Добавление новых строк в такую выборку также меняет её
актуальность; простое сравнение старых строк было бы недостаточным.

API возвращает `input_freshness`:

| Значение | Действие |
|---|---|
| `unchanged` | Выбранные входы и ревизии совпадают со снимком. Остальные проверки утверждения плана по-прежнему обязательны. |
| `changed` | Входы изменились; пересчитать затронутый прогноз и/или закупку, проверить новый результат. |
| `unknown` | Сохранённых сведений недостаточно, например у старого расчёта; выполнить новый расчёт. |

`input_provenance` группирует входы по типу и партии, даёт ссылки на доступные
детали импорта и `legacy_record_count` для строк без связанного источника. Актуальность
снимка и известность исходного файла — разные сведения: новый расчёт может точно
зафиксировать прежние строки и при этом честно показывать их неизвестное происхождение.
Ссылка на смешанную партию не обходит ограничения филиалов и может вернуть `404`.

Новый approve плана с изменёнными входами блокируется `409 INPUTS_CHANGED`, с
непроверяемым снимком — `409 INPUTS_UNVERIFIED`. Повтор прежнего успешно завершённого
approve с тем же ключом возвращает прежнюю квитанцию. Уже утверждённый план после
коррекции не переписывается и не отменяется автоматически: решение и его audit
остаются историей, а текущая актуальность отображается отдельно. Новое решение
принимается по новому расчёту. Утверждение не отправляет заказ поставщику.

Эта инструкция описывает поведение кода; выполненные проверки и ограничения среды
фиксируются отдельно в [PROGRESS](../../templates/PROGRESS.md) и
[FINAL_REPORT](../../FINAL_REPORT.md). Наличие миграции и хешей само по себе не
подтверждает внедрение у реального бизнеса или промышленную готовность.
